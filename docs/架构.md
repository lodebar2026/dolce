> **技术栈、怎么构建、为什么这么分层、哪些决策不要推翻**。要做什么见 [需求.md](需求.md)；

## 技术栈与构建

| 层 | 选型 |
|---|---|
| 外壳 | Tauri 2（Rust） |
| 前端 | TypeScript + Vite |
| 编辑器 | CodeMirror 6 |
| `.jpwabc` 解析 | 手写词法（`crates/dolce-formats/src/jpw/lex.rs`，门面 `src/jpword/lex.ts`，见 [源格式-jpwabc](模块/源格式-jpwabc.md)） |
| 渲染 | 原生 SVG DOM |
| 字体 | Bravura（SMuFL，`public/redist/`）+ 系统中文字体 |

前置：Node ≥ 20、Rust（含 cargo）。

```bash
npm install
npm run dev            # Vite 开发服务器（仅前端）
npm run tauri dev      # 跑桌面应用（需 Rust）
npm run build          # tsc 严格检查 + 打包（out/dist/，Tauri 的 frontendDist 与 Pages 部署都取这里）
npm run build:cli      # vite.cli.config.ts：Node ESM（out/cli/）给无头脚本 import；排版走 out/cli/engrave.js（不起浏览器）
npm run build:wasm     # wasm（不入库）：网页版识别（crates/omr-wasm + PDFium → public/redist/omr/，桌面版跳过）与编辑器开机就载的 dolce-wasm（crates/dolce-wasm → public/redist/dolce/，网页、桌面、Node 的 out/cli 都要；.jcx 编解码的码表单出一份 dolce_jcx_wasm 同目录、网页按需载）；dev / build 开头自动调，`node scripts/build-wasm.mjs dolce` 只编后两份（走 `crates/Cargo.toml` 的 `wasm-dolce` 编译档：fat LTO，不过 wasm-opt——它让 gzip 后反而变大；按体积编量过太慢，见该档注释）。要 `rustup target add wasm32-unknown-unknown` 与同版本的 wasm-bindgen-cli
npm run build:native   # Node 侧量字原生模块 native/textmeasure（macOS CoreText / Windows DirectWrite，要 Rust）
npm test               # 单元测试（vitest 直接跑 src 源码；配置与用例在本地私有仓库）
cd crates && cargo test   # 识别（Rust 工作区）单元测试；识别回归 `cargo run --release -p dolce-omr-cli -- regress <档>`，见「识别-Rust」
npx tsc --noEmit       # 仅类型检查
cd src-tauri && cargo check   # 仅检查 Rust 侧
```

**程序产出一律放 `out/`**（整个目录不入库）：`dist/` 网页构建、`cli/` Node 侧构建、`pkg/` OMR 分发包、
`vision-ocr` 编译出的 Swift 工具，以及 `../dev/scripts` 回归与成书脚本的报告和缓存（`pdf/`、`staff/`、`pptx/`、
`pdf-diff/`、`pdf-pages/`、`phrase-cache/`、`pdf-layout.json` …）。新脚本的输出也往这里写，别再在仓库根下另开目录；
Rust 的 `src-tauri/target/` 照 cargo 惯例不动。

## 1. 架构决策（已定，勿轻易推翻）

| # | 决策 | 理由 |
|---|---|---|
| A1 | **渲染用 SVG**（不是 Canvas 2D / CanvasKit） | 页面树（`PageItem`/`Group`/`GraphicPath`/`GraphicLine`/`TextFrame`）直接映射 SVG DOM；矢量、可点选、可导出 |
| A2 | **测量后端可注入，量的是画出来的那支字** | 排版只经 `src/common/measure.ts` 量字，底层由注入的后端给：app 用浏览器（`measure.browser.ts`：SVG `getComputedTextLength` + canvas 墨迹，与渲染同一引擎）；Node（回归、出图，`cli/engrave.ts` 装配）用系统文字引擎（原生模块 `native/textmeasure`，实现在 `crates/dolce-text-native`：macOS CoreText、Windows DirectWrite），口径对齐浏览器——泛称按中文页面解析、SVG 空白折叠、`text-spacing-trim` 的相邻标点挤压、单字 advance 取 1/64；没有原生模块的平台退回字体文件（fontkit + opentype.js，`measure.font.ts`）。**回归以 Node 为准**，与浏览器的差在亚像素（一次性对账见本地私有仓库的 `layout-node-parity.mjs`）。不要 CanvasKit、不要 DPI 位图缩放 |
| A3 | **排版、渲染、模型、编辑全在前端 TS；识别全在 Rust** | 排版/渲染/模型/编辑都在 TS，同一套代码跑 Web 与桌面（**迁 Rust 进行中**：演唱顺序、断句、试听时间轴、MIDI 写出、`.jcx` 编解码、ABC 家族（123 / ABC / jcx）读写、格式能力表与丢失清单、断行读写、简谱排版行视图已在 `crates/dolce-play`、`dolce-formats`、`dolce-model`、`dolce-view`，网页与桌面经主线程 dolce-wasm 同步调，TS 侧只留门面 `score/play.ts`、`common/jcx.ts`、`abcfamily/parse.ts` / `emit.ts`、`convert/capability.ts`、`model/breaks.ts`、`jianpu/slots.ts`）；识别（简谱、五线谱、混排、歌本切分）在 Rust 工作区 `crates/`，桌面版原生调、网页版编 wasm、命令行 `omr-cli`，三端同一个入口 `omr-engine`，结果交 TS 落地（`omr/`） |
| A4 | **桌面外壳的 Rust 只做原生能力** | PDF 导出（`svg2pdf` + `lopdf`）、识别（`crates/omr-engine`，OCR 走 ONNX Runtime 原生会话池、PDF 走 PDFium）、macOS MIDI 播放；文件 IO 与对话框用 Tauri 插件。Node 侧另有一个 N-API 模块，只给回归与出图用、不进 app：`native/textmeasure`（系统文字引擎量字与字形轮廓） |
| A5 | **一个语义模型 `ScoreDoc`，排版引擎只吃它的投影** | 各格式读进同一份模型，引擎输入（简谱的排版行视图 `jianpu/slots.ts::docView`、五线谱版面态 `StaffLayout`）由它投影、不另存语义；MusicXML 存回时没改过给原文，改过整份重写（不再 patch）。**MusicXML 独有的表层不进模型**：读入端把模型对象按身份（`_oid`）绑到原节点，原树与绑定表留在 Rust（`crates/dolce-model` 的 `xmlsurface`，TS 镜像经 `model/rustdoc.ts` 旁表记身份），五线谱引擎经查询函数（`model/xmlsurface.ts` 门面）现读，写出端按「写出端管的」之外通用回填。**MusicXML 只有一份写出端**（Rust `toxml`，TS 门面 `model/toxml.ts`），读写 MusicXML 不用浏览器 DOM（自有 XML 树 `crates/dolce-xml`） |
| A6 | **识别两条路线共用底层 crate，只向下依赖** | 简谱（`omr-jianpu`）、五线谱含混排与矢量档（`omr-staff`）共用 `omr-core`（图像、几何、像素内核）、`omr-sheet`（谱面元素、原语、曲线、满拍）、`omr-text`（文法、页眉、歌词）、`omr-ocr`、`omr-source`（PDFium 取数）；原语只写一份，两路各自的判据留在各自 crate。TS 侧的 `omr/` 只做结果落地，不含判据 |

## 3. 两个共用契约

**改这两处要格外当心——它们是多条路的交汇点。**

### 3.1 `ScorePainter`（`src/layout/painter.ts`）

全项目**唯一的排版器**：按请求排版并提交结果，管页面渲染（DOM 映射）、点选与播放高亮。请求两种——
简谱（`JianpuPaintRequest`：整份 `ScoreDoc` 交给简谱引擎 `layout/jianpu/`，简谱 / 投影档，各种格式同一条；帮助谱例、PPTX 也走它，
成书经 `pdflayout/browser.ts` 直接调引擎）、五线谱 / 混排（`StaffPaintRequest`，异步、带版本核验）。
排页算法各在各的模块，这里只管请求版本、结果提交（`LayoutResult`，`layout/result.ts`）与交互状态；
交互查询一律按**元素 id + 遍次**（`entryEl` / `lyricEl` / `partEls` / `highlight` / `pageOf` / `headerParts`），
身份索引按图元上的身份标签收（`pagetree/identity.ts` / `scoreindex.ts`），播放线在 `layout/playhead.ts`。
简谱走同步 `loadSync`（构造时 SMuFL 字体已就绪，不需要等资源），只有五线谱／混排是异步、带版本核验；目前没有路径需要为其余部分等待资源，真要等资源时再把
重排链（`App.reload` → `App._reloadScoreDoc` / `.jpwabc` 适配器的 `reload`）Promise 化。

### 3.2 `walkPageItem`（`src/pagetree/walk.ts`）

页面树的**唯一遍历骨架**，四个消费者共用：SVG DOM 两路（`svgVisitor` / `mixedVisitor`）、
成书 DrawList（`pdflayout/browser.ts`）、PPTX 形状（`editor/pptx.ts`）。

> 骨架只管「怎么走」，**坐标与颜色语义由各自 visitor 决定**——`mixedVisitor` 把 matrix 加在**叶子**上、
> 线与文字写死 black、只递归 Group；`svgVisitor` 每个 item 都产生 `<g>`、颜色取 item、无条件递归。
> **这些差别不许收进骨架。**

## 4. 数据流

| 源 | 路径 |
|---|---|
| `.jpwabc` | `JpwFile.fromString` → `jpwToScoreDoc` → `ScoreDoc` → `ScorePainter`（简谱引擎，简谱／投影；`.Layout` 只管投影档） |
| `.123` | `parse123` → `ScoreDoc` →（`jianpu/slots.ts` 排版行视图）→ `ScorePainter`（简谱引擎，简谱／投影，单声部多声部同一条） |
| 文本谱 | `parseFanqie` → `ScoreDoc`（内部经语法树 `parseFanqieAst` → `fanqieToScoreDoc`）→ 同 `.123`；乐句重排读模型上的原文区间改写原文 |
| MusicXML | 打开：`loadScoreDoc` → `ScoreDoc` → 同 `.123`（简谱档）／同一份 `ScoreDoc` → `layoutStaff` → `StaffLayout`（版面态）→ `ScorePainter`（五线谱/混排），**无代码区**；改动经 `toxml.ts` 整份重写 |
| `.abc` | `parseAbc` → `ScoreDoc` → 同 `.123`；读不动直接报错 |
| `.jcx` | `decodeJcx`（`crates/dolce-formats/src/jcxcodec.rs`，GBK/BIG5/UTF-8）→ `parseJcx`（ABC 家族第三个方言）→ `ScoreDoc` → 同 `.123`；写出 `emitJcx` → `encodeJcx`（`%MUSE2` + GBK） |
| `.jly` | `parseJly`（`crates/dolce-formats/src/jly/fromjly.rs`，门面 `jly/fromjly.ts`）→ `ScoreDoc` → 同 `.123`；写出 `emitJly`（`jly/tojly.ts`，走简谱输入模型 `jianpuInputOfDoc` / `jianpuInputOfJpw`）；「按乐句重排」只重断曲行（`rewrapJlyText`） |
| MIDI | `crates/dolce-formats/src/midi/`（`smf.rs` 读事件 → `import.rs` 量化建模，门面 `midi/import.ts`）（MusicXML 形状的 `ScoreDoc`）→ `toxml.ts` → 同 MusicXML 打开（`editor/midi-import.ts`，转成设置里的默认编辑格式）；不另写 MusicXML 写出端 |
| 简谱图片/PDF | Rust 识别（`omr-jianpu`）→ `RecognizedScore` → `omr-todoc::jianpu` → `ScoreDoc` → 123 核对文本（或 JPWABC / ABC / 文本谱 / jianpu-ly / Muse `.jcx`，同一张转换目标表） |
| 五线谱 PDF / 图片 | Rust 识别（`omr-staff`：位图 / 矢量 / 转曲矢量三档同一条路线，混排页带简谱互证）→ MusicXML + 核对 JSON（`omrrust/adapter.ts`）→ `loadScoreDoc` → 混排视图（谱面上改模型） |
| 成书 | MusicXML → `ScoreDoc`（`pdflayout/browser.ts::bookDocOf`，只留主旋律）+ 断句（`dolce-view/src/phrasedoc.rs`，断点按元素 id 写回文档）→ 简谱引擎 `book` 开关 → 页面树 → DrawList → PDF |
| 试听/MIDI | `ScoreDoc` → `dolce-view/src/playsong.rs::play_source_of`（按形状分给 `playSourceOfDoc` / `playSourceOfSong`）→ `buildTimeline`，高亮按元素 id |

## 6. 两条主线

### 6.1 模型主线

**已收敛到一个模型**：`src/model/doc.ts` 的 `ScoreDoc` 装得下和弦、力度、多声部、版面坐标、断行，
六种格式都读进它、从它写出。两个排版引擎各自只留引擎内部结构：

| 引擎 | 读什么 | 内部结构 |
|---|---|---|
| 简谱（`layout/jianpu/`） | 整份 `ScoreDoc` 的排版行视图（`jianpu/slots.ts::docView`：页 → 组 → 声部行，元素带 id），多声部同一条 | 定位结构 `PlacedPage` / `PlacedGroup` / `PlacedVoice`（`place/model.ts`），绘制出类型化图元 |
| 五线谱混排（`mixed/`） | `mixed/layout.ts::layoutStaff` 从 `ScoreDoc` 建的版面态 | `StaffLayout` 及各 `*Layout` 节点（带 `src` 引用模型元素） |

派生量（唱名、减时线、调号上下文、演唱顺序）不存进模型，经查询层取（`model/jianpu.ts`、`crates/dolce-play/src/playorder.rs`）。
`jianpu/jianpuinput.ts` 投影出的 `JScore`（`layout/input.ts`）不再喂排版引擎，只留给 jianpu-ly 写出、断句、识别对歌词这些按「和弦序列」处理的地方。
分工、判据与改模型要守的原则见 [模块/模型-scoredoc.md](模块/模型-scoredoc.md)。

### 6.2 样式主线

**入口收成一个**：`src/style/` 的 `StyleSheet`。内置主题（`themes.ts`：projection / print / book / staff）
叠上用户层（编辑器面板），或歌本样式表（`.ss`；成书的 `BookStyle` 也由它算出），
经 `cascade.ts::computeStyle` 按上下文（档位 / 引擎 / 分页 / 页位 / 段号）得到 computed 样式表，再由适配器折成尺子：

| 尺子 | 位置 | 适配器 | 服务对象 |
|---|---|---|---|
| `JianpuStyle` | `src/engrave/jianpustyle.ts` | `style/jianpu.ts::jianpuStyleOf`（预设 original / pptx）；成书 `style/book.ts::bookJianpuStyle(BookStyle)` | **简谱一个引擎、一把尺子**：各格式的简谱档、投影档、PPTX、成书。全是 pt；引擎另带按音符字号缩放的栅格（`layout/jianpu/metrics.ts::JianpuGrid`，挂着这把尺子） |
| `MixedOptions` | `src/mixed/model.ts` | `style/staff.ts` | 五线谱 / 混排（tenths） |

同一档里各格式用同一套样式值（用户定，2026-10 简谱合并：原先简谱引擎 `LayoutOptions` 与原样文档布局 `JianpuMetrics` 两把尺子、
同一份谱换个格式字号线宽都变；`dev/scripts/ruler-compare.mjs` 逐项核对各格式生效值全等）。
`BookStyle` 只是成书的输入数据（从原书统计中位数得来），折成 `JianpuStyle` 后与别的档同一个引擎。
`MixedOptions` 不并入，也不从 `JianpuStyle` 折算（用户定 2026-10-14）：同名键在样式表层面已经两边共享（`style/keys.ts` 两列都填），混排走自己那条级联（`editor/app.ts::staffStyle`），简谱档的风格、音符字体、和弦升降号不进来，几项出厂值也照混排自己的（见 [样式机制.md](样式机制.md) §1）。

**谱面元素的规则不跟着尺子分家**：同一种元素（八度点、临时记号、连音、弧、歌词音节…）怎么画、相对数字墨迹盒落在哪，
只在 `src/engrave/` 写一份；两个引擎把自己的尺子折成元素的参数（字号、墨迹高、颜色、线宽）、给出锚点坐标，
横向排布、分页、上方带堆叠这些**整行级**算法才留在引擎里。改一种元素的观感改 `engrave/`，两路一起变，
别在某个引擎里另写一份（详见 [排版-谱面元素](模块/排版-谱面元素.md)）。

**简谱引擎两段式**：`place/` 只定位（只碰注入进来的量具 `InkMeasurer`，所有 y 在这一段定死），`compose/` 只绘制（产出类型化图元、打身份标签）。
播放与身份索引不在引擎里：引擎只给图元打 `ItemIdentity` 标签，`layout/scoreindex.ts` 收、`layout/playhead.ts` 管播放线。
