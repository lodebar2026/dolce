# 五线谱识别（`src/staffomr/` + `src/omrkit/vectext.ts`）

**文字层完整**的印刷五线谱 PDF（Finale / Sibelius 直出）→ MusicXML。
移植自原 C++ 工程的 `qtomr/`（不在本仓库），改行为前先核对那边的原文。

底本是「赞美之泉」全系列谱本 PDF（761 页），GT 是同一套曲目的 Finale 导出 `.musicxml`
（同目录还有 `.musx` 原件，不读）。**路径只写在 `../dev/scripts/node-harness.mjs` 一处**
（`ZMZQ_ROOT` / `ZMZQ_PDF` / `ZMZQ_GT_DIR`，env `ZMZQ` 覆盖）——别在别处再抄一遍。

## 与简谱那条矢量路（500 首）的分界

| | 500 首（`src/omrkit/vector.ts`） | 赞美之泉（`src/omrkit/vectext.ts` + `src/staffomr/`） |
|---|---|---|
| 底本 | 文字**全部转曲**，没有文字层 | 文字层齐全，音乐符号是**真字符** |
| 输入 | 路径对象 | 路径对象 + 字形（码位 + 轮廓） |
| 字典 | 轮廓 → **汉字** | 轮廓 → **SMuFL 语义名** |

两边共用矩阵/包围盒/DrawOPS 工具（`vector.ts`）与形状聚类（`glyphdict.ts` 的
`shapeKey` / `shapeSig` / `sigDistance`）。**别把两条路合并**：一本没有文字层、一本有，
识别的第一步就分岔了。

## 抽取层：`src/omrkit/vectext.ts`

`extractTextPage(page, OPS, opts) → VecTextRun[]`。一个 run = 一次 `showText`
（= 原 C++ 工程的一个 `fpdf::TextObj`），里面是逐字形的 `VecGlyph`。

三条要害：

1. **字形轮廓要靠 `disableFontFace: true`**。开了它 pdfjs 的 worker 才走 `buildFontPaths`，
   把轮廓以 `commonObjs` 的 `"<loadedName>_path_<fontChar>"` 送出来（DrawOPS 编码，
   字形坐标系 em=1、y 向上）。于是**紧包围盒与形状签名在纯 Node 里就能算**，
   不起浏览器、不用 canvas——这块顶替的是原 C++ 工程的 `TextObj::getWordBounds`（pdfium 逐字包围盒）。
   `../dev/scripts/node-harness.mjs::openPdf` 已经写死这个参数，别去掉。
   全书 520744 个字形里只有 4.2% 拿不到轮廓，全是**没内嵌的标准西文字体**（ArialMT/Helvetica…），
   那些按 advance × ascent/descent 估，够用。

2. **变换要照 pdfjs canvas 的 `showText`/`paintChar` 逐句复现**：

   ```
   设备 = base · Tm · T(curX, curY + rise) · S(hScale·dir, -1) · T(advance, 0) · S(size, -size)
   ```

   两处 `-1` / `-size` 都不能省（字形坐标 y 向上、文本坐标 y 向下，翻两次）。
   `setFont` 的 size 常常是 1，**真尺寸烘在文本矩阵里**，一律从最终矩阵取（`VecTextRun.sizeDev`）。

3. **`setTextMatrix` 只有一个参数、且是数组**（`args[0]`），与 `transform` 的六个散参不同。
   写成 `args` 会得到一串 NaN，而且不报错——整页字形全落在 (NaN, NaN)。

4. **`TD`（`setLeadingMoveText`）设的 leading 是 `+ty` 不是 `−ty`**。
   PDF 的 `TD` 等价于 `TL(-ty)` 再 `Td(tx,ty)`，而 pdfjs 的 `setLeading` 自己会取一次负，
   于是最终是 `+ty`。写反了随后每个 `T*`（`nextLine`）都走反方向——
   Sibelius 的符干是一串 `T*` 叠上去的，符号错了整根符干会掉到符头下面，
   于是「八分音符读成四分、二分读成全音符」。这一条修好，时值从 61.5% 跳到 80.3%。
   **核对办法**：拿 `page.getTextContent()` 的 `transform` 与自己算的原点逐项对——
   那是 pdfjs 里另一条独立的代码路径，对不上就是自己错了。

### 贴图字：造字区的汉字是 **JBIG2 位图**，不在文字层

这本书把**造字区的汉字**（禰 / 祢 一类，Big5 之外）不是当文字排，而是当 **JBIG2 位图**
贴进内容流（`q … cm /Im2 Do Q`）。全书 277 处、54 页。

**它们一度被判成「底本自己缺字」**——因为 `getDocument` 没给 `wasmUrl` 时 pdfjs 解不开
JBIG2，会**整个丢掉那个 XObject**（`Jbig2Error: JBig2 failed to initialize` →
`ignoring XObject`），于是文字层、`getTextContent`、算子流、连 poppler 的 `pdftotext`
里都什么都没有，两个 `showText` 之间正好空出一个字宽。查实的办法是**自己 inflate 内容流**
（绕开一切字体与图像处理）：

```
BT /TT2 1 Tf 25.2 0 0 25.2 243 736.32 Tm <1678>Tj ET          ← 願
q 25.2 0 0 22.08 268.2 732.84 cm /Im2 Do Q                     ← 祢（就在这儿）
BT /TT2 1 Tf 25.2 0 0 25.2 293.4 736.32 Tm <0abc08ab14dc>Tj ET ← 國降臨
```

于是 `../dev/scripts/node-harness.mjs::openPdf` **必须给 `wasmUrl`**。
（Node 的 `fetch` 不认 `file:`，wasm 其实没加载成功——pdfjs 随即退回自带的纯 JS 解码器
`jbig2_nowasm_fallback`，位图照样解得出来。要紧的是**把这个参数给出去**，不给连退路都不走。）

`vectext.ts::maskRun` 把每张蒙版包成一个**只有一个字形的文本 run**（假字体名 `#mask`），
带上归一化的 24×24 位图指纹；归行、断音节、挂到音符上照常走，不必另开一条路。
**蒙版的 0 是墨**（stencil mask 默认 `Decode [0 1]`，0 才落笔）。

定案在 `../dev/scripts/gen-staffmasks.mjs`，办法与正文字形字典同一套——**把未定的贴图字读成一个占位汉字**，
让它在歌词行里占住位子去对 GT，占位处 GT 是哪个字就投哪个字。
实测投票**一边倒**：129 个占位点里 128 票投「禰」。GT 教不到的（标题里的、没配上 GT 的曲子里的）
先按指纹汉明距离形近补（门槛 12%），剩下的裁图看原件、记进 `src/staffomr/maskmanual.json`
（`node ../dev/scripts/staff-crop.mjs <页> <x0,y0,x1,y1> out.png`）——那份表里值为空串表示
「一个字被切成上下两张图，这是下半片，不另算一个字」。

现状：**277 个贴图字定案 272 个（22 类里定案 17 类）**，未定的 5 个是 p655 那四条
「整行文字贴成一张图」与 p465 的一处（要 OCR 才认得，另说）。
接上之后歌词档 92.2% → **95.0%**，「GT 有而页面没有」的缺字从 167 处掉到 33 处。

> **`../dev/scripts/gen-stafflyrics.mjs` 要把 `masks` 原样带过去**：那一档不是靠轮廓聚类的，
> 重建字形类时别把它冲掉。
> 两者还要**交替跑**：贴图字补上 → 歌词行不再缺字 → 对齐不再错位 →
> 当初错位投出来的标注（把「求」标成「禰」的那种，全书三十来处）自己就纠回来了。

坐标系：本仓一律**设备坐标、y 向下**；原 C++ 工程全程是 PDF 用户坐标、y 向上
（`CFX_FloatRect.top > bottom`）。移植时凡纵向比较逐处翻，这是本次最容易出错的地方。

## 字形字典：`src/staffomr/`

### 为什么不能只查码位表原 C++ 工程查的是 pdfium 的 `UnicodeFromCharCode(code)`。实测**码位与 unicode 都不可靠**：
同一个字形因为分了多个子集，码位会是 207/161/156/157/37/11/7/8/10……
（排版软件按首次使用顺序重编码），ToUnicode 也跟着在 `U+153` 与「码位原样」之间摇摆。
全书 Maestro 有 113 个不同码位，其实只有 **83 个不同字形**。

**轮廓是逐位相同的**（同一份字体程序）。于是走 `glyphdict.ts` 那套：
全书 17 万个音乐字形 → **176 个形状类**，每类定一次语义，识别时纯查表。

### 三层定案（`../dev/scripts/gen-staffglyphs.mjs`）

1. `bootstrapByTable` —— 用 `symbolmap.ts` 的码位表自举（Maestro / Opus / 共用表，
   照搬原 C++ 工程 `qomr.cpp::getSmufl` 的内联表与 `omr/symbolmap.cpp`）。
2. `mergeTwins` —— 亚像素抖动让同一字形落成两个 `shapeKey` 时，按 32×32 签名归并、标注取齐。
3. `applyManual` —— `glyphmanual.json` 的人工规则，可信度最高，压在最后。
   **按 `family + unicode + 宽高（容差 0.02）` 匹配，不按 shapeKey**——哈希人改不动。

**键的优先次序要紧**：私用区剥掉 `0xF000` 之后的码点 > ToUnicode 原值 > **内容流码位**。
反过来会错：Opus 的 `U+F0C5`（= `0xC5` 十六分休止）子集码位恰好是 63（`'?'`），
而 `'?'` 在共用表里是低音谱号——先查码位就把十六分休止读成了 F 谱号。
同理 `U+F072`（十六分符尾）的码位是 48（`'0'`）、`U+F075`（下方延长记号）的码位是 49（`'1'`）。
自举还要按 **`(码位, unicode)` 配对**投票，别把两个集合做叉乘——那会让 A 子集的码位
配上 B 子集的 unicode，查出根本不存在的组合。

现状：**全书 176 类全部定案，未定 0 类 / 0 字形**，`StaffGlyphLookup.misses` 全书为 0。

### Anastasia 把结构件当字形画原 C++ 工程全仓没有 Anastasia（Sibelius 手写体）的映射表，41 类全靠人工确认表建。
建的过程中发现一条**会决定整条流水线**的事实：

> **Anastasia 那 115 页一条长横路径都没有**——谱线、符干、加线、小节线全是字形。

- `staff5Lines`（U+3D，1.01×1.02 em）：一个 em 的五线块，横向以 19.9pt 平铺成谱行。
- `stem`（U+BB，0.018×0.259）：一个线距高的竖段，同 x 上下堆成符干
  （实测 p21 x=343 处 y = 142.4/147.4/152.3/157.2/162.1 连成一串）。
- `legerLine`（U+5F，0.5×0.018）、`barlineSingle`（U+6C，0.025×1.018）、
  `bracket`（U+201C）+ `bracketTop`/`bracketBottom`（系统左端每处画两笔）。

所以 `findStaves` **不能只找路径横线**，三条来源都要认：路径长横线（Maestro/Opus 页）、
`staff5Lines` 字形（Anastasia 页）。

半休止与全休止在字体里是**同一个方块**，靠落在第几线分（原 C++ 工程也是这么办的）。

## 识别流水线（`src/staffomr/`）

逐文件对应原 C++ 工程的 `qtomr/`，调用顺序照 `Score::process`，**别调**：

| 本仓 | 原 C++ 工程 | 内容 |
|---|---|---|
| `model.ts` | `qomr.h` | `PObj` / `Sym` / `Seg` / `Staff` / `SSystem` / `Bar` / `SPage`、盒运算 |
| `vecgeom.ts` | `pdfpp.cpp` 的 `PathObj` 谓词 | 子路径拆分、`isHLine/isVLine`、细矩形取中心线 |
| `page.ts` | `qomr.cpp` 的 `Page::findXxx` | 符号 → 谱行 → 符头 → 符干 → 符尾 → 小节线 → 系统 → 小节 |
| `notedata.ts` | `NoteData.cpp` + `findClefKeyTime` | 谱号/调号/拍号/临时记号/附点/符杠 → 音高与时值 |
| `toxml.ts` | `toxml.cpp` | 出 MusicXML（拼装复用 `score/xmlutil.ts`） |

### 一切几何门槛都是**小节线高度 H** 的比例

与简谱那条路同一个口径（`layout/jpglyph.ts`：「一切长度都是小节线高度 H 的比例」）。
**不许写绝对点值**——同一本书里谱表大小差一倍（正谱一格 5.4pt、小谱一格 2.7pt）。

H 怎么量：取**音乐字体的字号中位数**（`page.ts::estimateBarlineHeight`）。
Maestro/Opus/Anastasia 与 SMuFL 同源，都约定 em = 谱表高度 = 小节线高度，
所以字号直接就是 H——而「多短的段算段」「重描合并的容差」这些门槛在找谱线**之前**就要用，
等不到 `normalStaffSpace`。谱线找出来之后 `normalStaffSpace`（实测的一个线距）才是更准的那个。

### 线段层：一个 path 对象里可能有整行谱原 C++ 工程里一个 pdfium PageObject 就是一条线，标记挂在对象上。本书不然：
有一批 PDF（Finale 经 Distiller）把**整行谱的五条线加小节线全画进一个 path 对象**
（实测一个对象 400 个点、几十条独立直线）。所以先按子路径拆成 `Seg`，
**标记挂在段上**——凡原 C++ 工程写 `o->addTag(...)` 的地方本仓都是 `seg.addTag(...)`。

同一批 PDF 还把**填充**也画成密排细线：一条线用 `lw≈0.05H` 描五六遍、每遍偏一点凑出视觉线宽，
符杠更是几十道细线堆出来的。于是要 `mergeRedrawn`：

- **只在同一个 path 对象内部合并**。跨对象合并会把谱线与压在它上面的符杠串成一条粗「线」，
  那一行谱的线距就废了（实测 p185 第二线因此偏 1.2pt，整行谱找不出来）。
- 合并要求长轴方向**真的重叠**，不是首尾相接——同一条 y 上的加线与谱线是相接的两条，
  接起来会把加线并进谱线。
- 合并后的线宽取「重描的跨度」与「最大原始线宽」中的大者，那才是视觉线宽。

### 找谱行：三条来源、四道判据

来源：① 路径谱线；② `staff5Lines` 字形平铺（Anastasia，见上）；③ 打击谱的单条横线。

路径那一路**不照原 C++ 工程按「左端点 x 相同」分组找连续五条**，本书两处会崴：
第一线与第五线常比中间三条往左多探出一点（系统线的收口），左端并不相同；
重描合并偶尔把一条线拆成两簇，「连续五条」会被多出来的候选顶掉。
改成「拿第 i 条当顶线，试它后面几条各自定线距 d，再去 y+2d/3d/4d 附近找（容差 0.2d）」。

四道判据缺一不可（每条都是拿具体页换来的）：

1. **长度**：候选横段长度 ≥ 整页最长横线的 35%。符杠转成横段后混进来会把搜索打乱（p100 只找出 3 行里的 2 行）。
2. **线距区间**：`0.1H ≤ d ≤ 0.4H`。没有上限的话，吉他和弦图的品格线会被逐个系统各取一条，
   凑出一条从 y273 拉到 y590 的假谱行（p40，音高全废）。
3. **横向重叠**：五条线的 x 区间交集 ≥ 最短那条的 80%。
4. **长宽比**：谱行宽度 ≥ 4 × 谱表高度。和弦图是 14×16pt 的方块、五条品格线也均匀，
   只靠「等距五条」分不开，靠这条分得开。

### 加线：`abs(step)/2-2` 是**整数除**

`findLegers` 里原 C++ 工程写的是 `cnt = abs(step)/2-2`——C++ 的**整数除法**让 |step| ≤ 5 时
`cnt ≤ 0`，于是「谱表外一两级」的音符（下加一间的 D4、上加一间的 G5）不需要任何加线就收，
因为它们本来就没有加线。移植成浮点除、再加一道 `need > 0` 的闸，这些音符会**全被丢掉**。

代价不止是少认音符：丢掉的符头连带它的符干也无人认领，那根符干随后被当成小节线
（实测 p100 在 x=409 处凭空多出一条）。修好这一条，全书音符从 7.18 万涨到 8.01 万、
小节时值自检从 51% 涨到 69%、逐首音符准确率从 89.3% 涨到 93.4%。
**这是整条流水线上单条判据收益最大的一处。**

### 加线的**上限按符头宽**，不按线距

候选横段要有个长度上限，否则吉他和弦图的格线（本书每首歌上方都有一排）会被当成加线，
把图里的黑点收成谱表上方的高音符头。但上限写成「三个线距」就把**全音符**筛掉了
——全音符的符头有两个线距宽，加线跟着长。判据改成「加线不会比它托着的**符头**宽出三倍」，
线距那个上限只留作粗筛。

### Anastasia 的加线也是字形

同谱线、符干、小节线：那 115 页的加线是 `legerLine` 字形，路径里一条都没有。
不把它们也当成横段，谱表外的符头就永远没有加线撑着，`findLegers` 一律判否——
实测下加一线上下的 C4/B3 整批丢掉，一首歌漏十来个音，
**逐首音符准确率 93.3% → 96.9%、能进「数目相当」的曲子从 63 首涨到 77 首**。
符干那一路早就有 `glyphStems`，加线这一路当初漏了。

### 判音高用**墨迹中心**，不是基线原 C++ 工程用 `Symbol::pos.y`（字形基线），那是因为它只认 Maestro 一系
——那一系符头的基线正落在符头中心高度上。本书还有 Anastasia，字形原点约定不同：
实测它的 gClef 基线落在**第一线**（-4 级）而不是 G 线（-2 级）。照基线算：
谱号会被 `abs(middleStep) < 4` 判掉（整页一个谱号都认不出），符头整首低八度。
墨迹中心不依赖任何字体的原点约定——符头是个椭圆，中心就是它骑的那条线/间。
谱号归属也同理改判**墨迹与谱表的纵向重叠**，不判基线落在第几线。

`ClefSig::middleStep()` 的那三个数（gClef 41 / fClef 29 / gClef8vb 34）照抄原 C++ 工程：
序号 = (octave + 1) × 7 + stepIdx（C0 D1 E2 F3 G4 A5 B6）。

### 符杠去重

同一条符杠会被两条路各认一遍（实心四边形那条 + 密排细线合并成的粗横段那条）。
不去重的话时值每多算一条就减半——实测 p100 出了一堆 1/64。按 H/8 的粒度去重。

### 斜符杠是**一叠平行细线**

这一批 PDF 连填充也拿密排细线画（同 `Seg` 那一层的由来）。平的符杠叠出来还能
并成一条横段，`Seg.isH` 收得到；**斜的每条细线 y 都不同**，`isH`/`isV` 两头不沾，
整条符杠没人认，于是那些页「八分音符读成四分」——实测 p185~p204 一带，
一首歌能错六成的时值。

判据是「同起讫 x、同斜率、y 一层层错开」，这正是填充算法吐出来的样子：
按 (x0, x1, 斜率) 归组，组内按 y 排序、相邻不超过 0.3 格算同一条，
一束要有三条以上（一条是渐强线之类），厚度落在 0.2~1.2 格。
**只收斜的**——平的那种由横段那条路收，两头都收会把同一条符杠算两遍，层数翻倍、时值减半。

修好之后：**时值 86.3% → 95.2%，全书小节时值自检 82.2% → 87.6%**（Maestro 那 541 页 86.1% → 93.4%）。

### 音符排序：**先谱行、再 x**

只按 x 排会把一页里几行谱的音符横向交织在一起。顺序一乱，与 GT 的逐音比对就全废
——实测准确率会从 66% 掉到 26%。

### 符干有两种画法

Maestro/Opus 页的符干是路径竖线；**Anastasia 页的符干是一串 `stem` 字形**
（一个线距高的竖段沿 y 堆出来）。两种都要落成 `Seg`，否则那 115 页一根符干都取不到，
时值全错。拼接判据：同 x 一列，纵向**相接**（间隙不到半格）的一串算一根。

### 符杠分层与时值

照 `System::analyzeBeam` + `BeamGroup::calcLevel` 移植：符杠先按「共享符干且 x 区间重叠」
归组，组内按「离符头那一端有多远」排序，逐条隔开四分之一格就升一层。

**两处刻意背离原文**，都是拿实测换来的：

1. **组内排序按「到符头端的距离」，不按 `Stem::up`**。符干与符头常有重叠，
   原文那条判据（符干是否伸到符头之上）会误判；一误判整组的层就反过来，
   十六分与八分互换。
2. **一个音符的层数 = 这根符干上「有几个不同的层」，不是「最高的那一层」**。
   `calcLevel` 把整组符杠外推到组左端的 x 处比高低，靠右那条短符杠一外推，
   斜率误差被放大、层就判高了，于是只压着一条符杠的符干拿到「第 2 层」，
   八分读成十六分（全书时值 71.7% → 70.3%）。数「不同的层」两头都占：
   同一条符杠被拆成两段时（同层）只算一次，外推判错层也只影响编号、不影响个数。
   `staffOmrOptions.beamLevels` 可以切回「数穿过符干几条」的老做法做对比。
3. **内层符杠的接法：容差朝符头一侧放宽**（`beamConnect`）。原文只认「符干的**某一端**
   落在符杠一格以内」——可**第二、三条符杠是往符头方向叠上去的**，每条约四分之三格，
   离符干末端一格开外就整条接不上，层数只剩一层。实测 p27 那条十六分符杠离符干末端
   5.2 点、一格是 5.07 点，差这么一点点被判掉。改成再补一个窗口：从符干**离符头远的
   那一端**朝符头量，两格以内都算接上（三条符杠正好一格半）；反方向不放宽，那一侧
   不该有符杠。这一条吃掉了全书时值的头号错误——「十六分读成八分」158 处 → 15 处，
   时值 95.1% → 96.7%。

符干本身有两种画法（见上一节），符尾（`Tail`）优先于符杠。

### 和弦里的附加音

领唱谱的引子常是柱状和弦（同一根符干上叠三四个音）。同一行谱上 x 差不到半个符头的
一撮音算**一个和弦**：最高的那个是主旋律，其余标 `chordExtra` →
MusicXML 里带 `<chord/>`，对拍时不进旋律序列。不这么办的话，一段引子就能把
整首的音符序列顶偏，与 GT 逐音比对全废。

### 升降号：调号 + 小节内延续（`calcAlters` ← `Bar::calcAlter`）

MusicXML 的 `<alter>` 要的是**发声**的升降，`<accidental>` 才是谱面上印出来的那个记号。
两者不是一回事——G 调里一个没印记号的 F 也要写 `<alter>1</alter>`。三层叠加：

1. **调号**——升降号作用于所有八度的那个音名，整首有效（五度圈次序照原 C++ 工程的 `circle[]`）；
2. **小节内延续**——印在某个音左边的临时记号，对**同一小节、同一八度**的后续同名音继续有效；
3. 本位号把前两层都抹掉。

本行没印调号的沿用上一行（`analyzeBarData` 的 prev 逻辑）。
不算这一层的话，凡是带升降号的调导出的音高就是错的
（A 大调那一页的 C♯/G♯/F♯ 全会写成本位）。

### 演奏法、力度与连音（`notations.ts` ← `findNotations` / `findTuplet`）

原 C++ 工程到「打标」为止就结束了；挂到音符上、写进 MusicXML 是本仓新加的。

- 演奏法（重音/断音/保持/延长记号/颤音/换气）挂到**同一行谱里 x 最近**的那个音符
  ——记号印在符头正上或正下，横向偏差极小，纵向差多少都可能（要绕开符干符杠），
  所以只按 x 找。实测 400~600 页那一段 23/23 重音、5/5 保持音都挂对了。
- 力度记号走 `<direction>`，不挂在音符的 `<notations>` 里；容差放到三格
  （它不必对准某个符头）。
- 连音记号（三连音的「3」）：**乐谱字体的 `tuplet3` 字形**与**普通文本的单个数字**都要认。
  原 C++ 工程靠字体名 `Times-BoldItalic` 认，本仓不认字体名——同一本书里那个数字换过好几种字体。
  找到之后把该符杠盖住的符干上的音符全标成 n 连音，时值按 `normal/actual` 缩短。

#### 数字量到「**符头盒 ∪ 符杠盒**」，不是量到符杠中心线

连音数字总是贴在这一组的**外缘**，但贴哪一边看符干朝向：符干朝上时符杠在上、
数字压在符杠上方；符干**朝下**时符杠在下、数字在符头上方，中间隔着整个谱表加两截符干。

原来那道「数字中心到符杠中心线 ≤ 两倍字高」（约 2.7 格）只覆盖前一种，
后一种实测是 **5.5~9.8 格**，整批出局——Opus p726 一页 34 个三连音只收进 8 个，
剩下的时值全按普通八分算，小节自然凑不满（差额恰好是三连音的修正量）。

改成量到「符头盒 ∪ 符杠盒」这个**并集**，容差一格半。数字无论贴哪一边，
离并集都只有一格半，而 x 区间重叠但在**别的谱行**上的符杠（同一页上下两行的 x
范围本来就一样）离得 39~48 格，照样出局。

**试过更差、别再试**：只量到符头盒，「数字紧贴符杠」那种反被挤掉（p132 原本收到的
7 组全丢）；取「到符头盒」与「到符杠中心线」的**较小值**等于把两个宽门槛并起来，
假连音跟着涌进来（Maestro 一下掉 60 个小节）。容差扫过 1.5 / 2 / 2.5 格，
全书自检 **91.4% / 91.1% / 90.7%**——再放宽收到的 Opus 那十来个小节，
抵不过 Maestro 涌进来的假连音。

#### 没有符杠的连音：找**方括号**

四分音符以上的连音不打符杠，改画一条方括号（一条横线、两端各一截朝符头的短竖，
中间被数字断开）。原 C++ 工程认不出这种，本仓补一条：数字左右各找一截未归属的横段，
两截同高（y 差不到半格）、与数字同高（差不到一格半）、各自离数字不超过两格；
括号跨度定出音符范围，取跨度内音符数**正好等于 n** 的那行谱。

正好等于 n 才认——多了少了都说明括号找错了。宁可不认：不认只是这一组时值偏长，
认错会把邻组的时值一起改坏。

实测 p30/p31/p132/p133/p172 整页的三连音都是这一种（p30 一页 20 个数字），
补上之后全书自检 **89.8% → 90.8%**、Maestro **93.7% → 95.0%**。

### 拍号**逐小节**生效，不是逐行

一行谱上可能变拍好几次（实测 Opus 那本 p663 的第三行里 4/4 → 2/4 → 4/4）。
`timeSignatures` 返回一行上的**全部**拍号（按 x 排），`checkBars` 与 `toxml.ts`
都按「小节右界之前最后一处」取。按整行取最左那处的话，那些页整行的时值全错
——Opus 那 68 页的小节自检因此从 23% 涨到 57%。

### 小节线：判「盖满谱行」，不判端点恰在第一/第五线原 C++ 工程判的是「上端正好在第五线、下端正好在第一线」（`middleStep` 恰为 ±4）。
那条在**大谱表**上不成立：钢琴/SATB 的小节线贯穿两行谱，对上面那行来说下端远在 −4 之外
——实测 Opus 那 68 页（都是大谱表）因此一条小节线都没认出来，整页只切出一个小节。
改判「盖满」（容差四分之一格）之后，那些页从每页 9 个小节涨到 33 个。
另加三道闸：

- **贴着某个符头左右缘的竖线是符干**，不是小节线。
- 符干还要求**符头落在它的某一端**（一格以内），不能在中段——小节线擦着符头过是常事，
  不挡这一道真小节线会被当成符干抢走（实测 p227 每行只剩三个小节，音符全挤在一起）。
- 「短小节线」（与别处小节线同 x 的残段，原 C++ 工程用来收钢琴谱中间那截）**长度要够**
  （至少半个谱表高）：`barX` 是整页共用的，别的谱行上的小节线 x 会把这一行上
  一两 pt 长的碎段也收成小节线，随后就在那儿切一刀（实测 p351 一行切出 14 个小节）。

**试过但更差的一条**：「两端正好压在第五线与第一线上的竖线是小节线、不是符干」
——符头落在第一线、符干朝上伸到第五线的情形太常见，那条会把大批真符干判掉
（全书小节自检 80.1% → 75.9%）。代码里留了注释，别再试第二遍。

### 小节切分与小节线样式（`barlines.ts` ← `System::analyzeMeasures`）

两条小节线**挨得比两个线距还近就是同一处**（细+粗的终止线、反复线的两笔）。
门槛原先取半个线距，实测会在终止线处切出一个 4pt 宽、一个音符都没有的空小节。
同一笔还常被**重描好几遍**（实测 p205 的终止线画了 8 遍），归组前先按 x 去重。

样式判据：一处里有**粗**笔（线宽超过三分之一线距）就是 `light-heavy`（终止/反复），
两笔就是 `light-light`（复纵线），单笔不写 `<bar-style>`。

**反复点**这一档原 C++ 工程没做。本书的反复点用 `augmentationDot` 字形（Maestro 一路）
或 `repeatDots`（Anastasia 一路），两种都要认：谱表第二三间里上下两枚点，
在小节线**左边**是 `:|`（收，记在小节右端）、右边是 `|:`（起，记在**下一小节**的左端）。
认出来之后要给这些点打上标，免得附点那一步再把它们当成附点。

两枚 `augmentationDot` 成对还要两条（位图独唱谱，2026-09-27）：**中点落在谱表中线 0.3 格内、上下相距不到 1.5 格**
（夹着第三线）；只有一道细线的一处，点要**贴着线一格内**（有粗线或两笔时照旧两格）。
三度和弦的两个附点也上下隔一格，右边两格就是小节线，原来被当成反复点、附点整批丢掉
（我灵镇静 m4 A4/F4 在第一二间、m12 B♭4/G4 正在第二三间，还多出 3 个假反复）。独唱谱时值 90.84 → 90.94%，矢量路与合唱谱不动。

### 附点：**逐个附点找主人**

位图路找点（`dots.ts::findDots`）在去线图上取连通块：贴着谱线的点常连着一截线的残渣，
盒高超限或伸出窗口就整个丢了（我灵镇静 m3）。现在每块算两套盒——全部像素、不计谱线行的像素——
先按原样判，不过再按去线那套判，后者尺寸下限 0.3 格（符尾尖贴线的碎渣去掉线行只剩三四个像素，像个小点，
主使我喜乐因此多出两个附点）。独唱谱音符 +0.03、时值 +0.03。

二度错排的附点和弦（恩友歌 C5/A4/G4 附点四分，干夹在两列头之间，三个点一列）还有三处：
- `findDots` 判「同列另一个点有自己的主人」时，主人可以是左右半格内的邻列头（`TWIN_COL`）：两列头盒不重叠，
  右列头的点原来被当成反复记号的双点剔掉；
- 上方一格多内紧挨着另一个和弦头的，窗口下沿放到 0.75 格（`DOT_BELOW_STACKED`）：上方的间被邻头的点占了，
  最低音的点写在下方的间（全局放到 0.6 试过，合唱谱扫描自检 −2.2）；
- `attachDots` 的和弦右缘，两列之间容 0.3 格（原 2 像素，右列头左缘常差三个像素）。
原来这几个头没挂干、按落单头随和弦继承了附点，看不出来；实心头补上干以后才露出来。
取块的窗口上下各多放 0.3 格（`DOT_PAD`），再只留中心落在原窗口里的：窗口沿正切在点的边上时，一两个毛刺像素伸出窗口
就整块作废（齐来称颂低音谱表 C♯4/A3 附点二分，两个点都这么丢了）。独唱谱时值 +0.13，无一首掉；合唱谱不动。
试过「同一根干上的头附点取最多的」：净 +0.15，但 GT 里有两个声部共干、只一个声部附点的写法（赞美三一真神、信心使我得胜），撤了。

反过来（逐个音符找点）会出两种错：同一枚点被左右两个音符各认一次（时值凭空多出来）；
而线上音符的附点按惯例写在**上方那个间**里（差半格），纵向容差不够就整个漏掉。

### 拍号：分簇 + 跨页继承

一行谱上可能有两处拍号（曲中变拍），把所有数字一股脑拼起来会得出 `2424/4444`
这种东西（实测全书出过 32 处）——**先按 x 分簇再取最左那一簇**。
续页不再印拍号，所以 `recognizeStaffPage` 要把「这一页最后生效的拍号」传给下一页
（`opts.carryTime` / 返回的 `carryTime`）；不传的话全书 724 个有谱表的页里有 240 页
会退回默认的 4/4。

### 小节时值自检（`checkBars` ← `Bar::checkFull`）

**不靠 GT 的自检**：小节里的时值凑不凑得满拍号（`checkFull` 的成败）。凑不满就说明
这一小节里有音符读错了（时值、漏音、多音）。全书都能用，不限于对上 GT 的那 110 首。

现状 **14697/16076（91.4%）**。天然对不上的有三类，不算错：整小节休止、弱起、
跨行断开的小节。`node ../dev/scripts/staff-report.mjs` 打印这个数，**并按刻谱软件分档**
——三家的谱面习惯差得远，一锅平均看不出改动打在哪一路上。

**注意它不是单调的**：小节线多认出来一批，分母跟着涨，比率可能反而降
（Opus 那 68 页刚接上时就是这样：对得上的绝对数从 8621 涨到 9040，比率却从 55.1% 掉到 50.8%）。
看的时候要**同时看绝对数与比率**。

按刻谱软件分：**Maestro 95.7%（541 页）、Anastasia 88.8%（115 页）、Opus 67.1%（68 页）**。
（拍号逐小节生效之前是 74% / 65% / 57%；和弦层与连音两处改完之前是 93.3% / 87.2% / 60.1%。）

## 圆滑线与连音线（`slur.ts`）

移植自 `findSlurTies` / `analyzeSlurTie` / `SlurTie::checkTie`，另加 `findWedges`。

**弧有三种画法，都要认**（原 C++ 工程只认第一种）：

1. 贝塞尔曲线的实心月牙（Finale 原生，`curves > 0`）；
2. **描边**的曲线（Sibelius/Anastasia）——只认填充的话那 115 页一条弧都没有；
3. **压平成多段折线的多边形**（经 Distiller 那一批，实测 p205 一条弧是 60 段直线围出来的、
   `curves` 恰好是 0）。折线段数取 12 当门槛：符杠是 4 点、矩形 4~5 点。

三道判据缺一不可：

- **落在系统线左边且与它纵向相交的曲线是谱表括号**，不是弧（照原文）。
- **弧又宽又扁**（宽 ≥ 1.2 格且宽 ≥ 高 ×1.5）。不加这条，吉他和弦图里的小圆点
  （2.3×2.3 的填充曲线，每页上百个）会全被当成弧——实测 p185 多出 177 条「圆滑线」。
- **渐强渐弱要先挑出来**（`findWedges`）：它们也是又宽又扁的图形。

挂两端照 `validateSlurNote`（纵向判据整段翻成 y 向下）。两端在谱表上**音级相同**的是连音线。

**跨行的弧要接回一条**：谱面上画成两段（上一行末、下一行头），GT 里是一对 start/stop。
不接的话会多出一个起点与一个终点——实测全书多认出三分之一的弧就是这么来的。

### **一条弧画成两个对象**：并回一条

这一批 PDF 把每条弧从极点处劈成左右两半，各是一个路径对象（实测 p170 的连音线
`(283.9,173.3)→(289.8,175.0)` 与 `(289.8,175.0)→(295.7,173.3)` 明明是同一条）。
不并回去的话每一半各自去找两端的音符，左半的右端落在弧顶下面那个音符上，
两端音高就不同了——**连音线整批读成圆滑线**（全书 113 处 `t→s` + 111 处 `T→S`），
弧的条数也比 GT 多出两成。

判据（`mergeArcHalves`）：前一条的右端与后一条的左端重合（五分之一格以内）、朝向相同，
且接口正好是**极点**——朝下的弧「前一段降、后一段升」，朝上的反过来。
极点这一条是要害：两条**真的相邻**的弧（前一条收在某个音符上、后一条从它起头）
端点也重合，但那里是两条弧各自的端，升降正好相反。
并完之后弧线 90.5% → 93.4%，条数 500 → 353（GT 413，剩下的差额转成了漏检）。

### 弧端离符头能有多远：三格，不是一格

原文（`validateSlurNote`）只许弧的端点离符头墨迹一格。本书不行：朝上的弧画在**符杠之上**、
朝下的弧画在符干末端之下，离符头两三格是常事，一格的窗口把那些端点全判掉、弧只剩一头挂着。
实测（弧线档 / 识别出的条数，GT 413 条）：1 格 93.4% / 353，2 格 93.9% / 382，
**3 格 94.1% / 402**，4 格 94.0% / 418——再放就开始乱挂了。

### 写出时的 `<slur number>`：按弧配对，跨页的半截在声部层面接

原来音符上只记「起 / 止」两个布尔值，编号按谱表号给（第 1 行谱 1 号、第 2 行谱 2 号）。同一行谱上两条弧交叠
（嵌套、上下两声部各一条）、或只认出一端的弧，读入端就配串了——MuseScore 导入牵我的手报
「No matching end found for start of slur number 2 in measure 24, instrument 6 … Older slur will be ignored」（五处）。现在：

- **每条弧一个弧号**（`markSlurNotes`），音符上记 `slurStartIds` / `slurStopIds`；写出时 `noteXml` 先带一个临时 `arc` 属性，
  整个声部写完后 `toxml.ts::renumberSlurs` 配对、重编号：一条弧先写出的那端占最小的空号，后写出的那端交还。
- **两端落在同一处的弧算同一条**：同一个音，或同一行谱上横向差不到半个符头宽（同一和弦的不同成员）。牵我的手每条弧都被检出两份；
  我灵镇静 m4 一条弧的终点挂在和弦的两个成员上（E4→A4、E4→F4）。原来两份同号、读入端只留一条，碰巧对了；
  逐条写出就成了两条（P1 弧数 46 → 91、我灵镇静 88.78 → 88.27），去重后回到原数。
- **跨行弧的两个半截**：页内的由 `reconnectSlurs` 接（前后两个系统行数相同、按行号对应）。接不上的
  ——首系统隐藏了人声谱表（4 行 vs 6 行）、跨页、中间某个系统这个声部的谱表隐藏——在**写出时按声部**接：
  `markSlurNotes` 给落单的半截按几何定 `end`（右端伸到本行最后一小节）/ `begin`（左端在本行第一小节前半）/ `mid`；
  `renumberSlurs` 把同一谱表号上的 `end` 接到**这个声部下一个出现的系统**（`sysOfBar`）里的 `begin`，朝向相同的优先。
  在写出时接是因为声部归属这时才定、跨页也连着，编辑器里改了「谱表 ↔ 声部」关联表重建 MusicXML 时会跟着重接。
- **只看「缺一端」就接是错的**：先试过「落单止点接最早的落单起点」，是爱 P1 m1 的起点被接到 m44 的止点、P2 m41 接到 m49，
  凭空造出横跨几十小节的弧（记号档掉分）；改「相隔 ≤N 小节」也只是猜（扫 1/2/3/4/6，各首互有涨落）。几何判据才是正路。
- **接不上的半截不写**：MusicXML 里半截弧没有合法写法，留着是一个永不闭合的编号。照写成另取的编号（起点 16~13、止点 12~9）
  与不写，回归各档一分不差——读入端 `model/fromxml.ts::MarkSink` 本来就把配不上对的半截丢掉。

**这一系统里某个声部的谱表全隐藏了**（Finale「隐藏空谱表」：牵我的手首系统只印了器乐，W / M 两行人声没印）：
`scoreToMusicXmlRaw` 原来整段跳过不写小节，这个声部从第二个系统起算第 1 小节、整体往前错一个系统（W / M 少开头 6 小节）。
现在照样按这一系统的小节数写整小节休止（`<rest measure="yes"/>`）：拍号、调号取同系统别的谱表的，谱号取这个声部第一次露面那一系统的；
头一个隐藏小节写 `<staff-details print-object="no"/>`，重新露面时写回 `yes`。`sysOfBar` 记 −1——隐藏的系统不算这个声部出现过，
接跨行弧时跳过它。合唱谱回归的 `chorus-opslib.mjs::recRows` 推识别侧小节号照同一个走法改。

代价：位图合唱谱三首各掉 1~2 步（宁静、望十架、破碎扫描）。原来**系统中间**缺一端的碎片（长弧只检出一截、别的笔画误当弧，
望十架 P3 m12 起 / m14 止）编号都是 1，读入端按「后起点顶掉前起点」碰巧拼成了 GT 上那条弧；现在不再靠撞号拼。
系统中间的半截要在位图那头的弧检测里补，见待办。

## 文本层（`textanalyze.ts`）

移植自 `qtomr/TextAnalyze.cpp`。**原 C++ 工程只打标、不导出**——它的 `toxml.cpp` 里
没有歌词也没有和弦；「把歌词逐字挂到音符上」「和弦拼回一个记号」是本仓新加的，
口径照简谱那条路（逐字挂音符，一行歌词 = 一个 verse）。

三处刻意背离原 C++ 工程的顺序与判据，每条都是拿具体页换来的：

1. **先判和弦记号，再判歌词**。原 C++ 工程的 `markHarmony` 只认三种形状（含 `/`、单个大写音名、
   `X Y`），本书的 `D m7` / `B♭Maj7` / `A dim/E♭` 一个都不沾边；而歌词那一步的判据
   （纵向跨过某条水平线）会把和弦一并收成歌词（实测 p100 的 `G` 被挂成第二段歌词）。
   记号语法复用简谱那条路的 `CHORD_TOKEN_RE`（根音必须大写），**两处要一起改**。
2. **`markHarmonySuffix` 提到歌词之前**。`Maj7` / `m7` / `dim` 是独立的文本对象，
   歌词那一步会先把它们收走，和弦只剩光根音。
3. **后缀的间隙门槛放到两格**（原 C++ 工程是根音盒高的一半 ≈ 0.7 格）。
   本书把和弦印成 `A dim/E♭`——根音与后缀之间有个空格，实测间隙 2 格；
   而同一行里相邻的两个和弦隔着十格开外，不会误并。

和弦的根音升降号是**乐谱字形**（`accidentalFlat`/`accidentalSharp`）混在文本里，
要插到根音**之后**（`Bb`、`F#`）——`harmonyxml.ts` 是这么解的；
往末尾追加会得到 `BMaj7b`，解不出来。

纯数字的音节不是歌词（是小节号与行首段号），一律剔掉。

### 中文歌词行的补锚

原 C++ 工程的 `markLyric` 只有两个锚点，而且都是**西文**的：带连字符的音节、
音节之间的延长线。这本书的中文歌词逐字一个音节、字与字之间既不连字也不拉线，
一整行下来一个锚点都没有——**整行歌词就此丢掉**（实测 p27 第一行谱下的
「田中的白鷺鷥無欠缺什麼」，那一首只剩后五行；p39 同）。

补的这一道是**自校准**的：拿这一页已经认定的歌词学出「字体 + 字号 + 离谱表底多远」，
同字体同字号、落在同一条带里（不越过下一行谱）的未定文本也算歌词。
不写绝对几何——那会把版权行、段落词、表情记号一并收进来。歌词 85.4% → 87.1%。

### 中文歌词的锚：对着符头的一排、同排换字体的字

延长线那一路原先把 `between` 的参数写反了（判成「字顶在锚线以下」），等于**任何一条水平线下方的文字都算歌词**——
页脚、版权行、小节号一并进来，靠后面剔数字、配对容错兜着；赞美之泉的中文歌词大半也是这样「顺带」收进来的。
照字面改正后歌词 94.95 → 86.98、同一版 66 → 21 首：中文歌词没有连字符、没有延长线，正经的锚一个都没有；
宣主荣耀那条「单字成排」认汉字，而这本书的中文多是坏 ToUnicode 的子集字体（抽出来是乱码），正则碰不上。
改正时补了三处，都不看字面：

- **对着符头的一排**：同字体同字号、同一条基线上三段以上，排在某行谱下方、没越过下一行谱，**过半的段正上方有那行谱的符头**。
  标题、页脚、版权行、段落词都碰不上「对着符头」。救回到 91.6。
- **同一排里换了字体的字**：「祢」常另印一段——造字区字体（EUDC），或抽不出文字的图像蒙版字（`#mask`，文本为空，靠 `textLookup` 按字形认）。
  竖向落在两个以上已认定歌词的字盒之内（放四分之一字高，有的字盒短一截：深触我心 p167「们」）、横向在谱表两端之内的，
  不论字体、有没有文字都并进来。横向不按那一排两端卡：行尾的「祢」常隔着几拍（我爱祢，我主 p153）。
- **补锚的符头那一路**：自校准原只收同字体、字号等于已知歌词中位数的；加一条「正对着符头、字号与某个已知歌词相同」，字体不论。
  中英对照页的中位数落在英文字号上，行尾弱起单印一段的「祢」（另一种字体，沙仑的玫瑰 p197）原先两头都够不着，被英文那排的「You」顶了位。

与改正前逐首比：两边都有的 74 首歌词逐首相同；变的三首都是变好——232 主的恩典乃是一生之久切曲对了（音符 0 → 78.6%，
新进「数目相当」）、254 求主充满我原先配成英文（50.8%）现在读出中文（89.2%）、266 祢的同在汉字占比过了门槛按中文算。
汇总档因分母变动：歌词 94.95 → 94.80（76 首）、同一版 66 → 68 首、数目相当 86 → 87 首（音符 97.77 → 97.55，全是新进的 232）。
合唱谱矢量档（宣主荣耀）仍 100%。`staff-report` 的「未归属对象」多了约 1700：原先被横线以下一律收成歌词的版权行、页脚等，现在不再算歌词。

### 全角空格：整字见方的墨迹却读出一个 ASCII 字符

这本书的歌词逐字一个文本对象，每个字旁边跟着一个字形，它的 ToUnicode 是 `!`、
轮廓是个空的字身框，量出来正好一个 em 见方（全书前 200 页就有 1754 个）。
它是**这套字体的全角空格**，不是字。

判据：`!bboxEstimated && 墨迹 ≥ 0.8 em 见方 && 查出来是单个 ASCII 字符`。
真的 ASCII 字母不会填满一个 em 见方，汉字则由字形字典给出汉字——这一条只会打中它。
（从前是**形近补字歪打正着**把它标成「1」、再被「纯数字不是歌词」那条剔掉的；
字典一重建就露馅，歌词里冒出一串 `!`。）

**「祢」是底本缺字，不是读错**：全书的「祢」在内容流里只有那个全角空格、没有任何墨迹
（`getTextContent` 与 `getOperatorList` 两路都核过，那一格确实什么都没画）。
于是「主我敬拜祢」只能读成「主我敬拜」。这一档记在缺字里，别再去几何层找原因。

## 坏 ToUnicode 的 CJK 字体：拿 GT 自举（`textglyphs.ts` + `../dev/scripts/gen-stafflyrics.mjs`）

本书有几档 CJK 字体的 ToUnicode 是坏的（`XA7E42585` / `X3A4DAD4C` / `DFYuan-Lt-HK-BF` /
`DFHei-Md-HKSCS-U`），读出来是乱码；`HelveticaExt-No` 更是整体 +1 位移
（`"Qsfdjpvt!Dsptt"` = `Precious Cross`）。修之前「对上的 100 首里 83 首歌词读成乱码」。

修法照 500 首那条建库路，但**条件好得多**：曲目已经按**音符序列**对上了 GT
（不依赖任何字体），于是每首歌都有一份「谱面这一串字形」↔「GT 这一串字」的对应，
逐字投票就能认出字形的真身，**不必先跑 OCR**。

要害五条：

- **票投繁体**。书上印的是繁体、GT 是简体，投简体会让字典把全书吐成简体
  ——那不是这本书的原文。用 `opencc-js/cn2t` 把 GT 转过去再投；对拍那一路自己做繁简归一。
- **一个音节一个字形才投**。汉字一字一形，而拉丁词一个音节好几个字母；
  拿一个汉字给四个字母各投一票，字母的类立刻被污染成一锅粥
  （实测「我:104 的:75 祢:69」曾同属一个字形类）。谱面那侧是 ASCII 的、
  墨迹不到半个字身的（标点），也都不投。
- **第一轮只收长度完全相等的段**。乱码文本让编辑距离的相等判据永远不成立，
  DP 退化成「全是替换」的对角线：长度相等时那正好是逐位对应（可信），
  长度不等时插入删除落在哪儿全凭运气。有了字典之后才有锚点，才允许长度不等，
  并要求**字典已认得的字里至少三成落在对角线上**。
- **标题要单独投**。标题用的是另一套显示字体（24~27pt 的黑体/圆体），
  与歌词字体不是同一批类，光靠歌词投票读不出标题。
- **要跑好几轮**，而且**接着上次的字典建**：字典好一分，中文标题就多认出几首，
  于是又有更多歌词可投票。实测四轮后收敛在约 1200 类。
- **认不得的小墨迹字形直接丢，不当字**。坏 ToUnicode 的字体里混着句读点、连字符、
  版权符号一类的小件；它们既投不出票（上一条），留在音节里就成了歌词中间凭空多出的字符。
  判据只看**墨迹高不到半个字身**——不看 unicode（那正是坏的）。
- **登记类的时候要逐字形带各自的签名与墨迹尺寸**（`../dev/scripts/staff-align.mjs::versesGlyphs` 的
  `metas`）。从前整个音节只带 `glyphs[0]` 那一份，多字形音节里后面那些字形就被登记成了
  首字形的签名——**形近补字照着错签名匹配**，把一个整字见方的类补成了窄竖条的「1」。
  签名错了，字典里那一类就再也扶不正。
- **投票要两档**：全票通过，或者「至少两票且占六成」。只要一票就定案会把对齐时的
  偶然错位刻进字典（同一个字形在别处再出现就跟着错）；只认全票又会漏掉真有异读的常用字
  （谱面同一个字形在不同曲子里对上「祢」和「你」是常事）。实测这两档比只认全票多出
  三百多类，歌词准确率不降反升。
- **形近补字只在最后一轮做**。`fuzzyFill` 是拿 32×32 签名把未定类匹配回已认得的类
  （同一个字印小一号 `shapeKey` 就变了，同 500 首那本）。放进轮次循环里会让本轮猜出来的字
  成为下一轮的锚点，错一个滚一串——实测掉到 63.3%；只在末轮做一次是 77.8%。

### OCR 兜底：`../dev/scripts/gen-staffocr.mjs`

自举只能标出**对上了 GT 的那些曲子的歌词里出现过**的字。全书 222 首只对上一百首，
剩下的字没人教——补完自举后，识别出的中文歌词里仍有 6.2% 是字典没覆盖的乱码。
这一步照 500 首那本的 `../dev/scripts/gen-glyphocr.mjs`：**每个未定类只送一次 OCR**，
因此哪怕全书 2 万个字形，也只有一千多次识别，十几秒跑完。

- 字典是按类 id 登记的（`TextGlyphBuilder.ensure`）、没存轮廓，所以脚本先**回头扫一遍书**
  把待办那些类的轮廓收齐，再送 OCR。
- 只收**恰好一个字符**、且落在「汉字 / 全角标点 / 数字字母」里的结果。
  多字符说明那一格切歪了；PaddleOCR 认不出时会吐 `■`/`□` 之类的占位符，
  收进字典就成了歌词里凭空多出的字。
- **要与自举交替跑**：OCR 补上的字让更多标题认得出来 → 更多曲子对上 GT → 更多歌词可投票。
  实测「自举 → OCR → 自举 → OCR」两个来回后收敛。

这是五线谱这条路里**唯一要起浏览器的建库步骤**（PaddleOCR 走 onnxruntime-web）；
产物落盘之后识别仍是纯查表、不碰 OCR。

现状：字典 1974 类、已定 1942，**覆盖 98.9% 的字形实例**；
歌词 **84.3%**（70 首谱面与 GT 同为中文）——另有 32 首谱面是**英文歌词版**
（这本书每首印两遍，见下），与中文 GT 不是同一版，不入分母。
真读不出来的（< 20%）只剩 4 首，都是配错了曲（见下），不是字形不认得。

    npm run build && npm run build:cli
    node ../dev/scripts/gen-stafflyrics.mjs --rounds=4 && node ../dev/scripts/gen-staffocr.mjs
    node ../dev/scripts/gen-stafflyrics.mjs --rounds=2 && node ../dev/scripts/gen-staffocr.mjs --min=1

### 没有 ToUnicode 的 CJK 字体：断音节按墨迹，不按码位（牵我的手）

Finale 经 Distiller 出的合唱谱，歌词字体是 `PMingLiU-ETen-B5-H` 子集、Identity-H、**根本没有 ToUnicode**：
pdf.js 把 CID 当码位吐出来（`ㇳ` `䘬` `ĭ` `Ἀ`），字典里也没有这套字形。乱码本身留给字典去认；
要先管住的是**断音节**——`splitSyllables` 原来按「码位落在汉字区段里」一字一音节，
这批码位大半落在区段外，被当成拉丁字母连成一个词，字间没印空格的一段（「恩惠慈愛」「在你」）整段挂到一个音上，
后面的字跟着错位（W 声部 48 处）。

- **墨迹宽过 0.6 em 的乱码字形当全角字**，一字一音节。实测汉字墨迹宽 ≥0.77 em、半角标点 ≤0.33 em，中间空得很开。
- **紧跟在全角字后面、宽不到 0.4 em 的乱码是半角标点**，丢掉。`;`（0.13×0.63 em）、`?`（0.33×0.74 em）偏高，
  「墨迹两向都不到半个字身才丢」那一条拦不住，原来自成一个音节、白占一个音（`走?` 的问号挂到了下一个二分音符上）。
  只在「上一个是全角字、当前不在拉丁词中间」时丢，拉丁词里的重音字母不受影响。
- 位图路合成的对象（`#` 字体）、没有轮廓的估算盒不走这两条。

认字（字典里没有这套字形）走 `../dev/scripts/gen-chorusglyphs.mjs`：合唱谱一曲一个 PDF、GT 逐声部，
配法与赞美之泉不同，另起一份——识别交出的 MusicXML 与 GT 逐声部逐段取音节序列，**两边音节数相等才逐位投票**，
声部按「同段同长」配（同长的有几段取同编号），定案规则同 `TextGlyphBuilder.finish`，字典里已定案的类不改、冲突打印出来。
牵我的手补进 PMingLiU 113 类（同一个字按 `shapeKey` 落成几类），歌词档 −44.6% → 100%（字典就是拿这份 GT 投出来的，
量同一份当然全对；换一首同字体的谱，这批字能直接认，没出现过的字仍是乱码）。

### 页脚文字块、首系统的乐器全名

同一本每页底部印着版权声明四行（英文一行、中文两行、网址一行），原来被收成了 Piano 的歌词（每页十来个音节），
首系统左边的乐器全名「Piano」「Synthesizer」也被收成了歌词：

- **页脚**：「正上方那行谱在它的横向范围里一个符头都没有」那条判据在这里用不上（最后一行是钢琴，下面全是音）；
  中文那两行一字一个对象，还被「一字一段排成一排」收成歌词锚，`(www…/copyright)` 带 `/` 会被当和弦。
  改在判和弦、判歌词**之前**先挑出来归文本框：最后一行谱以下、**整行连排**（相邻两段间隙不到一个字号）、
  **行中心在页面中线上**（两格内）。四行的中心都是 306pt（页宽 612 的一半），而谱表中线在 321pt 上下——
  量谱表中线差了四格，所以拿页宽。歌词对着音符散开排，整行连在一起的只有成段文字。
- **乐器全名**：原来只挡「在全页最左那行谱的左边线以左」，首系统缩进，全名在后面几个系统的左边线以右。
  改为比**同一高度那几行谱**（纵向离谱表不到一个谱表高）的左边线。

### 和弦带：一个文字对象里的几个和弦、排练号、长音中途换和弦

同一本的 Bass 声部和弦（PDF 文字层 120 个根音段），原来出 88 个，三处病根：

- **一次 TJ 印了好几个和弦**，中间只隔一大段空白（`A    E/G♯`、`A    B`）。按整个对象判：
  `AE/G` 被当一个和弦（升号还插到了根音后面，成 `A#E/G`），`AB` 不合文法被收成歌词。
  改成按**字形间隙**切段（`glyphPieces`，间隙过 2 格就断，与「两个对象相距 2 格内才并」同口径），
  判和弦时「逐段都合文法」也算；拼后缀、插升降号都按段来。
- **升降号插到它左边紧挨着的那个字母后面**（逐字右缘），转位低音的 `E/G♯` 才落对；原来一律插在第一个字母后面。
  拿不到逐字位置的位图路合成对象照旧。
- **长音上中途换和弦**（全音符上 `F♯m … F♯7`、`B sus4 … B`）：附近没有空着的音，原来直接丢。
  改为挂到这一刻还在响的那个音（同小节、和弦左边最近），按横向位置折成音内的偏移（量到下一个音或小节线），
  写出 `<harmony><offset>`，偏移取整到拍（二分及更长按四分、短音按八分）。只开在矢量路，位图路照旧丢。
- **方框排练号**（`[A]` `[B]`）是单个大写字母、合和弦文法，在「方框字」那一步之前就被和弦抢走（Violin 上挂了三个和弦）。
  判和弦的两处（`isWholeChord` 与原工程的 `markHarmony`）都先挡掉被贴身框圈住的字：框比字大不出两格才算，
  大框（文字框、版面边框）里的和弦照收。这本的框是**填充**画的（外矩形套内矩形一圈），不能只认描边。

修完 120/120。

**斜的连音方括号**：同一本的四分三连音（人声 W/M 共 11 小节）括号顺着音高走，两截各斜 1.8~2.8pt，
而 `segsOf` 只收水平、竖直两种段（谱线、符干、小节线都靠这一点，不能放宽），`bracketGroup` 一截也找不到，
那几小节整小节多出一拍。改为在数字附近（左右 12 格、上下 2 格）的未打标路径里另收斜段（括号是「横线 + 一截钩」一笔折线），
斜率 ≤0.5、长过一格；两截要**共线**：数字两侧的内端点同高（差不到半格）、斜率差不到 0.15——楔形线一正一负过不了。
修完 W/M 全部满拍。

另：音乐字体里取出的速度文字（`= 60` 的音符与数字是 Maestro 字形，没映射）会吐 `\x03` 一类控制字符，
原样写进 XML 整份文件读不开——`score/xmlutil.ts::escapeXml` 改为剔掉 XML 1.0 不许出现的字符。节拍器仍认不出，记在待办。

### 谱行归属：**先试音符上方那行**

`findStaffForNote` 里原 C++ 工程的 `stfA` 是「音符挂在它下面」的那行谱（y 向上时 `dist<0`），
先试它、再试 `stfB`。y 向下要**反过来判符号**，照抄会把次序调个个儿——
大谱表里挂在顶行下沿的音符会先去试下面那行谱。

### 声部与小节内起点：和弦层（`initChords` / `checkFull` / `splitVoice`）

**时值与声部是同一件事。** 一个小节里写两个声部时，光看「音符时值加起来是不是拍号」
永远对不上（两个声部各自凑满，合起来是两倍）；而要分声部，先得知道每个音**从第几拍起**
——那正是 `checkFull` 算出来的 `offset`。

调用顺序照原 C++ 工程 `Score::analyzeBarData`（`NoteData.cpp`）：
`initChords` → `checkFull(false)` → 失败再 `checkFull(true)` → **成功才** `splitVoice`。
`initChords` 在 `buildNotes` 里做（符干还在手里），后三步在 `checkBars` 里
——三连音（`findTuplets`）在 `buildNotes` **之后**才按比例改时值，早算的 offset 会是错的。

#### `guessDur` 不用另写

`buildNotes` 早就把符头形状、符尾/符杠层数、附点、三连音一并算进了 `StaffNote.duration`，
那就是原文 `Chord::guessDur(true,true)` 的结果。**别再照原文抄一份**——半休止 vs 全休止
按第几线判、层数数「不同的层」而不是「最高的层」，这些判据都是拿具体页换来的，
抄第二份必然走样。

#### `initChords`：先按**符干**归，无符干的再按盒相交归

原文只按符干归（无符干的符头各自成和弦，靠 `checkFull` 的时间列再并到一起）。
本仓多一步，因为本仓要出 `<chord/>`：领唱谱的前奏常是柱状全音符和弦，不归的话
导出成先后几个音、时值全乱。

**主音取最低的那个**：MusicXML 里一个和弦的第一个 `<note>` 不带 `<chord/>`，
刻谱软件写和弦是**自下而上**的，所以那个是最低音。一度取最高音（想着「主旋律在上面」），
与 GT 的口径正好反着——改过来之后音符 97.3% → 97.8%、音高 97.25% → 97.7%、
「同一版」全对的曲子 29 → 30 首（位图路 60.6% → 61.1%）。

按符干归顺带修掉老 `markChords`（判「x 差不到半个符头宽」）的漏洞：**二度和弦**的
两个符头错开画在符干两侧，x 差整整一个符头宽，那条判据认不出来；按符干归就没这问题。

**同一根符干断成两段的，两枚和弦要并回一枚。** 位图路上一根长符干常常断成两段
（去谱线、抹加线各啃一道），`findStems` 于是给出两条符干，按符干归就归成
**两枚和弦**——起点相同，`splitVoice` 只能把它们分到两层，下面那个成了第二声部，
而逐声部对拍只取声部号最小的那一路。**钢琴左手的八度几乎全栽在这上面**：
实测破碎 p3 m22 那个 C3/C2 八度，两个头各自「和弦 1 个音、有符干」，
逐音比下来就是「识别比 GT 高七级」（那一行的读错里 +7 是最多的一档）。
判据：同一行谱、两条符干的 x 差不到 **0.3 格**（谱面上就是一根）、
纵向搭得上或断口不超过一格。位图路按谱行 92.71% → **93.23%**
（破碎钢琴左手 86.1% → **91.5%**、右手 86.6% → 87.9%）；矢量路各档不动。
x 容差扫过 0.15 / 0.2 / **0.3** / 0.4 / 0.5 / 0.7 / 1.0 格：
93.23 / 93.23 / **93.23** / 93.21 / 93.13 / 93.09 / 92.86%——**再宽就并错了**。

**没挂上符干的孤头要并回同 x 的那枚和弦。** 位图路上符干常常够不着最外那个头
（符干段的两端被去墨啃掉、`extendVSegs` 那 0.35 格续不到；二度的头还错开画在另一侧），
落单的头于是自成一枚**没有符干**的和弦，与真和弦**起点相同**——`splitVoice`
按 (offset, dur) 贪心分层，同起点的两枚只能分到两层，落单那个就成了第二声部；
而逐声部对拍**只取声部号最小的那一路**，它整个落在分母外，谱面上的最低音也就没了。
判据只认「本来就该是一枚」的：同一行谱、x 上与和弦贴着（错开画的二度也只差一个符头宽）、
纵向与和弦里最近的那个头**不超过一格半**、音级差 1~3 级
（同高的是重复检出不并；再远就是另一路旋律，那才该分声部）。
门槛（`ORPHAN_STEP` / `ORPHAN_DY`）：并回符干那一条落地之后重扫过
音级≤3 & 纵向≤1.6 格 / 音级≤5 & ≤2.0 格 / **音级≤5 & ≤3.0 格** / 音级≤7 & ≤3.0 格：
按谱行 93.19 / 93.20 / **93.23** / 93.23%。矢量路各档不动。

> **这一改动逼出了度量里的一处不对称**：GT 那侧（`node-harness.mjs` 的四个逐音序列
> 函数）原来**照收** `<chord/>` 附音，识别侧却一直只取主音（`staff-align.mjs` 的
> `!n.chordExtra`）——两边比的不是同一件事。原来被 `markChords` 漏认和弦掩盖着，
> 二度和弦一认出来就现形（071《我一生要赞美祢》一首就差 12 个音）。
> **两边一律只比主音序列**，倚音同理（GT 早就跳过 `<grace/>`，识别侧补上 `!n.grace`）。
> 口径一改基线整体下移（音符 97.73 → 97.26），那不是退化，是原来量错了。

#### 五条线的**线距要逐条重估**，不能一路拿第一段外推

`findStaves` 拿第 i 条当顶线、试后面几条各自当第二线定出线距 d，再去
`y + 2d / 3d / 4d` 附近找线（容差 `0.2d`）。**低分辨率的扫描件上五条线并不匀**
——实测望十架 p1 那行是 10 / 10.5 / 10.5 / 11 px，照第一段推到第五条，
误差累到 2.0px，正好卡在 `0.2d = 2.0` 的容差上，**差 0.02px 丢掉整行谱**。
那一页 10 行只出 9 行，`alignSections` 的行数序列随之整体错位一节，
后面每一行都在跟错的 GT 谱表比。

改成拿「已经找到的那几条的平均间距」往下推（`dd0 = (best.cy - 顶线.cy) / n`），
误差不再累积。真扫描件那一档音符 40.57% → **44.57%**；矢量路各档不动
（那边的底本线距是匀的，这一改一分不差）。

**还要补一条兜底：连着的五条、按平均间距等距就收。** 上面那一路推之前得先
**猜对第二线是哪一条**；线距更不匀的时候（实测望十架 p10 那行是 11 / 15 / 12 / 12 px），
第二线一取到 11 那条，第三线就推到 207 而真线在 211，差 4px 过不了容差，
再往后 d 一大又撞上「线距上限」的 `break`，整行谱就丢了。
而**按五条的平均间距判等距**（`staffline.ts::groupStaves` 那一套）分得出来：
平均 12.5，四段与它各差 1.5 / 2.5 / 0.5 / 0.5，都在两成以内。
补上之后望十架那份的谱行数 109 → **112**，与 GT 印出来的行数**完全相同**。

> **不能改成放松原来那条容差**：`0.2 → 0.3 / 0.4 / 0.5` 实测真扫描件
> 44.57% → 44.05%（三档一样）——多收进来的是别的东西，不是这一类。

#### `checkFull`：分**时间列**，每列取列内最小时值

1. 整小节休止（`restHBar`）与「本身就够一小节」的和弦单独收着，不进时间列；
2. 其余按 x 从左到右分时间列——与上一列的首和弦横向不相交就开新列，
   但两根**符干的间隙不到半个线距**时仍算同一列（两个声部的符干挨在一起）；
3. 每一列的时值取**列内最小**的那个（长音跨过后面几列），累加成 offset；
4. 总和正好等于拍号才提交，否则整小节判失败。

`ignoreSmall`（第二趟）把「单音、且符头明显比别人小」的和弦当**倚音**剔出去——
倚音不占拍子，算进去这一小节永远凑不满。全书只剔出 9 个，聊胜于无。

#### `splitVoice`：按 (offset, dur) 贪心分层

只在 `checkFull` 成功之后调——没有 offset 就无从分层。两个前置动作照原文：
无符干、且时值正好一小节的和弦**先并成一个**（SATB 的柱状全音符）；之后按
(offset, 盒顶) 排序。**原文比的是 y 向上的 `top`（大的在前），本仓 y 向下，翻过来。**

`offset >= now` 的和弦并入当前层，层号即声部号；剩下的开下一层。全书拆出 467 个
非第一声部的音符。

**孤零零一个占满整小节的和弦**（位图路误检的全音符 / 全休止）不算一个声部、并回第一声部——但**只并排在真声部前面的**：
排在前面才会把真旋律挤到第二声部去；排在后面的倒常是真的（合唱谱男低一个全音符、男高两个二分，Holy, Holy, Holy m8），
并回第一声部就接在男高后面，这小节成了八拍。

#### 兜底：`checkFull` 两趟都失败时按符干方向分

SATB 把女高女低挤在一行时，刻谱的通行约定是**上声部符干朝上、下声部朝下**。
门槛卡得很死，两条都是拿实测换来的：

- **只在单声部凑不满时才拆**；
- 拆完**两个声部都要正好凑满拍号**才认。

无条件按符干方向拆，全书小节自检从 80.1% 掉到 73.4%（普通旋律一小节里本来就上下都有符干）；
只要求一个声部凑满的话，另一个多半是硬切出来的，与 GT 逐音比对反而变差（音符 93.42% → 93.21%）。

#### 导出按 offset 出（`toxml.ts::emitVoices`）

同一声部的和弦按 offset 排；声部的第一个音不在小节头时先补 `<forward>`，中间有空档同样补
——多声部的谱面上第二声部常常从第二拍才起唱，不补的话它整段前移一拍。
声部之间照旧用 `<backup>` 倒回小节头。`checkFull` 没凑满的小节（`StaffChord.timed` 为假）
退回按顺序累加时值那条老路：没有 offset 可用，只能假定音符首尾相接。
按拍位排满的小节里，**提前收尾的声部补 `<forward>` 到小节末**：合唱谱女低、男低唱半小节就并回主声部的和弦（共用符干），
不补的话换行谱前按最长声部写的 `<backup>` 会倒过小节头。

**大谱表的声部号在整个 part 里编**：第 k 行谱的声部 v 写成 `(k-1)*4 + v`（下谱表 5、6，通行写法），多谱表时一律写 `<voice>`。
各行谱都从 1 编的话，上下谱表的 voice 1 被读成同一个声部，拍数自检把两行的时值加在一起，每小节都成了两倍
（Holy, Holy, Holy 识别后报 25 小节错拍）。

**起点不能用 `ticks`**：那个函数有 `Math.max(1, …)` 的下限（时值再短也得占一格），
拿它换算 `offset = 0` 会得到 1，于是每个从小节头起的声部都白白多出一个 1 格的 `<forward>`。

倚音出 `<grace/>` 且**不写 `<duration>`**——写了小节就超时长，回读的软件多半直接报错。

## 曲子一级：跨系统连接与声部（`score.ts` ← `Score::connectSystems`）

一首曲子印成好几个系统，**每个系统里的第 n 行谱是同一个声部**。不连起来的话，
钢琴谱的伴奏行会被当成一堆互不相干的谱行——本仓在移植这一层之前，导出只能挑每个系统的顶行，
**全书 7.2% 的音符（5796 个，钢琴/SATB 的伴奏）整批丢掉**。

`buildScore` 逐个系统与「当前状态」做一次 **LCS 对齐**（原 C++ 工程用 dtl 的 diff，这里手写一份），
比对的是**签名**（`StaffToken`：行首谱号 + 谱表大小档 + 在花括号的上半/下半）：
对上的接到同一个 `ScoreStaff` 上，新出现的另起一个，这一系统里没有的**留 null 占位**
（`makeHidenStaves` 那一档）——合唱谱常常在只有钢琴的段落省掉人声行，
不留位置的话后面所有行都会错位一格。

**分声部要在原文之外补一条**：花括号的上半另起一个声部、下半接着上一个（原文）；
但本书 Opus 那一路的花括号在页面上根本找不到（既不是路径也不是字形），
只靠原文那条判据钢琴谱的两行会各成一个声部。补的判据是刻谱的通行约定：
**同一系统里相邻的「G 谱号 + F 谱号」是大谱表**，合成一个声部。

导出走 `scoreToMusicXml`：一个 `Part` 出一个 `<part>`，多谱表声部写 `<staves>2` +
逐谱表的 `<clef number=n>`，每个音符带 `<staff>`，两行之间用 `<backup>` 把时间倒回小节头。
全书 47 页是大谱表，`node ../dev/scripts/staff-report.mjs` 会跑一遍导出冒烟（出错 0 页）。

## 八度移位与反复房号（`octave.ts`）

**八度移位**（`8va`/`8vb`）移植自 `findOctaveShift`：记号 + 一条**虚线** + 末端一个竖钩，
三件缺一不可（不然谱面上任何一条虚线都会变成八度移位）。只作用于**最近的那一行谱**
——把窗口里的谱行全移，大谱表上会连累另一行。
全书 18 段（12 页），移了 268 个音符。

**反复房号原 C++ 工程没做**，按同样的路数新加：谱表上方一条水平线、**左端**下垂的竖钩、
贴着钩的数字，三件齐全才认。落到 `Bar` 上出 `<ending>`（左端 start、右端 stop）。

**这一房罩着哪行谱，判据是「钩底贴着谱表顶」**，不是「横线离谱表多远」——横线的高度
取决于这一行上方还有没有歌词/和弦，能差出两倍谱表高（实测 p172 那条横线离谱顶 8.2 格，
原先卡在 5 格以内，整页房号一个都认不出）。**竖钩也不限长**：书上的钩有长有短，
p172 那条从横线一直垂到谱表顶、7.9 格，原先卡在 3 格以内。两条一起改之后
【数目相当】那 77 首的房号从 0 涨到 20/26。

八度移位与 GT 的差距**基本不是漏检**：抽查过 p85（GT 说有 4 个房号）
——谱面上一个房号都没有，那是 GT 那一版的编配不同；而 p463 谱面上确有 `1.`/`2.`，
我们出的 4 个 `<ending>` 与 GT 一致。八度移位同理：p76 的 `8va` 谱面上确实有，
GT 那一版没写，于是逐音比对反而差 0.17 个点——**记谱版本不同，不是读错**。

## 编辑器接入（`browser.ts` + `omrctl.ts`）

拖进来的 PDF 先判**该走哪条路**：`isStaffPdf` 取样几页，页面上有音乐字体的文字就走这条
（不栅格化、直接读文字层与矢量对象），否则退回简谱那条（`omrkit/decode.ts` 光栅化 + 连通域）。
与 `vector.ts::isVectorPdf` 互补：那条判的是「转曲的矢量谱」。

**产物只进混排视图**，不走 `importBytes`：那条路对单声部 MusicXML 会进简谱档，
而五线谱的和弦、多声部、slur 在简谱引擎输入里装不下——单声部时它直接抛
`measure has no chord`。所以 `OmrHost` 上加了一个专用能力 `adoptStaffXml`，
一律进混排；编辑器里的简谱文本只做 best-effort，**转不出来就不动**
（那可能是用户没存的稿子），并在状态栏说明。

字形字典由 Vite **动态 import** 打成单独的 chunk（glyphmap 183KB / lyricglyphs 269KB），
只在真跑这条路时加载——拷进 `public/` 会与源走味。

端到端检查：`node ../dev/scripts/staff-ui-check.mjs [页号]`（起 Edge，验「拖进来的 PDF 走没走对那条路、
产物落没落到混排」）。与 `../dev/scripts/staff-diff.mjs` 分工：那份量准确率，这份验接线。

## 对拍（`../dev/scripts/staff-diff.mjs` + `../dev/scripts/staff-align.mjs`）

**基准一律是 GT 的 musicxml**（单声部主旋律）。识别与曲目对齐在 `../dev/scripts/staff-align.mjs`
（与 `../dev/scripts/gen-stafflyrics.mjs` 共用，**对齐判据只写在那一处**），`../dev/scripts/staff-diff.mjs` 只做对拍与记账。

`--errors` 另出一份**逐条错误清单**（`staff-out/staff-errors.json`，带页码与盒）与错因排行；
判据在 `../dev/scripts/staff-errors.mjs`（位图路的 `chorus-diff.mjs` 共用同一份）。
**只收「数目相当」那一档**，与准确率的分母同口径：谱面用反复记号、GT 写成两遍的那些曲子
逐音对齐必然满屏「多出音符」，那是表述不一致不是读错，混进排行就把真错因淹掉了
（实测 2304 处里 2013 处出自这类曲子，「多出音符」一档虚高到 71%）。
拿这份清单出可翻阅的诊断报告：`node ../dev/scripts/gen-staff-analysis.mjs <曲名> --zmzq`。

- **切曲目范围**：先按判据找出**所有首页**（第一行谱之上有一条 ≥ 正文字号 1.6 倍的文本），
  相邻首页之间就是一首。只按「对上标题的那些」切会把中间没对上的曲子整个吞进来
  （实测 018 首从 159 个音涨到 384 个）。全书 464 个首页——这本「全系列」把每首歌
  印两遍（中文歌词一版、英文歌词一版）。
- **配对**：分数取「标题相同」「开头音符序列相似度」「中文歌词相似度」三者的较大者。
  - 标题一路要繁→简归一（`opencc-js/t2cn`）；英文一路兜底（GT 里只有 97/222 首写了英文名）。
  - 音符一路**不从头比**：谱面常常比 GT 多一段引子（p205 头一行是柱状和弦的前奏，
    GT 从第 5 小节起），从头比会被引子顶掉。改成拿 GT 的开头去谱面的前二十几个音里
    找最像的一个窗口。准确率那一档也照此允许跳过开头。
  - **不加单调约束**：本以为可以按曲号顺序对齐，实测不成立——这本 PDF 是几本册子拼起来的，
    后半段不按曲号走（152 首在 p281、010 首在 p467）。改按分数从高到低贪心。
  - 音符数差一倍以上的不配：开头三十几个音撞上是有可能的（同调同起句），
    整首长度差一倍就不是同一首。
  - **标题命中的是一组候选，不是一首**。全书有三组同名（075/135「耶稣爱你」、
    062/197「耶稣恩友」、110/162/212「主祷文」）；索引里一个键只存一首的话，
    另一首**永远配不上**——「标题已经指名别人就不许改判」那条会一票否决它。
    存成数组，同名的几首之间由开头音符相似度挑（分数从 0.9 起，仍压过所有非标题配对）。
- **门槛 0.65 是拿歌词扫出来的**。歌词是配对的照妖镜：配错了曲，歌词准确率立刻掉到 0，
  而音符相似度还能有个五六成（同调的赞美诗旋律本来就像）。
  实测 0.5 → 135 首但 62 首歌词全错；0.65 → 98 首、歌词全错降到 31 首。
- **歌词是仲裁，也是第三条配对通道**（有了字形字典之后就不循环了）：
  - **仲裁（否决）**：把「谱面与 GT 同为中文」的配对按歌词相似度排开，分档极干净——
    真配对最低 62%、错配最高 6%。于是取 **0.3** 当否决线：低于它就跳过这一对，
    谱面那一段与那首 GT **都还留在池子里**让别的配对认领
    （p85 的《耶稣爱你》就是这么从 135 改判到 075 的）。
    这道闸只在谱面**汉字占比过三成**时才开——光按「汉字够十个」判会误伤英文版页面
    （标题加版权行就凑够了，006《新造的人》音符 99% 却被判掉）。
  - **通道**：光靠「开头 32 个音」配，谱面多一段引子、改了前奏或头一行读坏就整首落空，
    而歌词照样读得出来、且几乎不会撞。歌词相似度 ≥ **0.45** 就直接配上，
    不必再过音符那道门槛。全对全比太贵（464 × 222），所以先按**字集 Jaccard** 粗筛
    （O(n)，只看用到哪些字）每段留前 8 首，再算编辑距离。
  - **中文版优先**：这本书每首印两遍，两版的标题都对得上 GT、音符也都像，
    光看这两样是平手，贪心会随手挑一版；挑到英文版就麻烦——那一版的编配常与 GT
    不是一回事，音符档白掉十几个点。所以歌词对上的那一段**加 0.05 分**
    （加分要小，只在平手时起作用）。从前试过按「歌词里有汉字」加分，没赚到：
    那只是「这一段有中文」，不是「这一段的中文与这首 GT 对得上」。
- **只取每个系统的顶行**：GT 是单声部，谱面上 SATB／钢琴谱一个系统有好几行，
  主旋律在最上面那行（不取顶行，152 首的音符数正好翻倍）。
- **「符头+符干+符尾」画成一个字形的音符要收编**（`page.ts::adoptCompositeNotes`）：
  Anastasia 偶尔这么画，码位映到 SMuFL 里本属**速度记号**的 `metNote8thUp` 一族，
  不在 `HEADS` 里于是整枚被跳过——**谱面上那个音就此消失**。全书 29 处
  （093《黑暗中的光芒》缺的三个音全是它）。三条判据：
  **只收落在谱表里的**（谱表外的是真的 `♩= 72`，全书 133 个 `metNoteQuarterUp` 里 116 个是那类）；
  **盒要收窄到符头**（音高判的是墨迹中心，拿整枚字形的中心去判会高出两三级）；
  **符干朝向从轮廓自己看出来**，别信码位表的名字——表里把朝上朝下都标成了 `…Up`，
  全书三个形状类里有两个其实是朝下的。看法是拿现成的 32×32 形状签名逐行数墨迹，
  最粗的那一行就是符头；**签名的行号是字形坐标、y 向上**（行 0 = 页面下沿），
  行号小 = 符头在下 = 符干朝上。
- **全休止与半休止是同一个方块**（`notedata.ts`）：字形字典分不开它们（轮廓逐位相同，
  一律标成了 `restHalf`），只能按落在第几线判——半休止**坐在中线上**（墨迹底贴中线），
  全休止**吊在上面一线下**（底比中线高一格）。不判的话整小节的全休止全读成半休止。
- **行首行末的空条不是小节**（`makeBars`）：谱行左端到第一根小节线之间只有谱号/调号/拍号
  （曲子起头印 `|:` 的尤其明显），终止线到谱线右端还常剩一小截（实测 p101 第二行剩 13pt）
  ——两头各切出一个「一个音符都没有」的小节，全书凭空多出 120 个。
  休止也带 `Note` 标记，所以「一个都没有」是真的空，整小节休止不会被误删；
  只动头尾两条，中间的空条留着（那多半是真读漏了，删掉反而看不见）。
  行首那条删掉时，它右端的样式要落到新首小节的**左端**（`Bar.leftStyle`，
  `light-heavy` → `heavy-light`），不然整首少一根结构性小节线。
  逐首小节数由 71/84 涨到 74/84。
- **斜杠符头不进旋律序列**（`StaffNote.slash`）：前奏/间奏整行写斜杠 + 和弦名的那种记号
  （`noteheadSlash*`）全落在谱表第三线上，当成音符就是一串 **B4 四分**——
  实测 088/094/102 三首各混进 16~19 个，是全书「多出来的音符」里最大的一类。
  MusicXML 那边照样出，但要带 `<notehead>slash</notehead>`（排在 `<stem>` 之后、
  `<staff>` 之前），不然回读又变回真 B4。剔掉之后「数目相当」由 77 首涨到 84 首。
- **「同一版」才是「给一份新谱能读到多准」的答案**。「数目相当」只保证两边长度接近，
  里头还混着**版本不同**的曲子：这本书有一批只印了英文歌词版，而 GT 是中文版，
  两版的编配本来就有出入（多一段间奏、尾句写法不同），那些差异不是识别错。
  分辨办法是**歌词**：谱面与 GT 同为中文、且歌词对得上八成以上，基本可以断定是同一份谱。
  两档差得很清楚——同一版 61 首**音符 98.6%**，谱面没有中文歌词的那 20 首只有 **94.6%**。
  `../dev/scripts/staff-diff.mjs` 把这一档单列，`same*` 几项也进了基线。
- **口径分档**（照 500 首那本的四类记账）：音符数与 GT 相差一成以内的算「数目相当」，
  只有这一档进准确率的分母；相差远的多半是两边结构不同（谱面用反复记号、GT 写成两遍），
  归「表述或结构不一致」另记。另外允许**整首平移一个八度**再比——
  记谱档次不同不算读错（238 首 How Great Thou Art 整首差一个八度）。
- **整首移调也照此办理**：这本书印的调常与 GT 不同（实测 272 首《耶和华尼西》谱面
  1 个升号、GT 4 个升号，143 个音齐刷刷高两个音级），那是移调版不是读错。
  **但不许自由拟合**——读错谱号同样是整首差一个常数，放开搜索就把它一并洗白了。
  所以平移量**只认调号差算出来的那一个**：识别侧数谱行首的升降号个数、GT 取 `<fifths>`，
  两者指到不同的主音时才按两个主音的音名距离平移（`../dev/scripts/staff-diff.mjs::keyShift`）。
  这一条把 272 首从「音符 23.1%」纠正回它本来的水平，全书音符 96.9% → 97.9%。
  **含升降的音高那一档不能把升降号原样带着平移**（`shiftPitch`）：移调之后调号变了，
  同一个音级该带的升降也跟着变——G 大调的 `F♯` 移到 E 大调是 `A♮`，原样带过去成了 `A♯`。
  保持不变的是「相对调号的偏离」（临时记号），所以
  `新升降 = 原升降 − 原调给原音名的升降 + 新调给新音名的升降`。
  不这么算，272 首的音高档只有 46.2% 而音符档是 96.5%——那不是读错，是口径没跟着移调。
- 基线在 `testdata/赞美之泉/staff-baseline.json`，任一档变差即失败（`--bless` 重写）。

**为什么只对上 110/222**：拿没配上的 112 首逐首去所有**没被认领**的谱段里找最佳，
歌词相似度最高只有 36%、音符最高 59%——**根本没有候选**。也就是说 GT 里剩下的曲子
要么不在这本 PDF 里、要么是另一种编配。这是**语料的性质**，不是判据的缺口；
把门槛压低只会换来一堆歌词全错的假配对。

## 合唱谱：宣主荣耀三声部（Finale 直出、macOS 打印成 PDF）

合唱谱语料里唯一的矢量谱（`dev/testdata/合唱谱/宣主荣耀三声部/`）：女高、女低、男声三行人声（方括号）+ 钢琴大谱表（花括号），
两页四个系统。音乐字体是老 Maestro（MacRoman 码位），文字层 ToUnicode 齐全。整曲识别抽到 `staffomr/song.ts::recognizeStaffDoc`
（编辑器 `browser.ts` 与回归 `chorus-ops.mjs` 共用），`chorus-ops` 单列「矢量谱」一档。几何流水线一处没改就能出谱（85 小节自检全满），
要补的都在结构与文字：

- **Maestro 'p' 是 p**：码位表原来照原 C++ 工程写成 mf（「合字」），实测 'p' 宽 0.5 em、'F'（mf）0.86 em，两个字形。赞美之泉没用过 'p'。
- **花括号**：Finale 画成上下两半两条又窄又高的曲线（各 5×36 点），过不了弧的「又宽又扁」形状闸、走不到判括号那一步。
  在形状闸之前收（系统线左边、高 ≥ 4 格且 ≥ 宽的三倍），`tokenOf` 把上下相接的两半并成一个。
- **「相邻 G + F 谱号是大谱表」只在系统里一处花括号都没认出时兜底**：女低（G）与男声（F）相邻，按谱号并就成了一个大谱表。
- **声部名**：谱表左边、纵向落在五线里的文字原来被当成谱内元素挡在 `collectTexts` 外（只认出印在两行之间的「Piano」），
  加了横向条件；`score.ts::nameParts` 按系统落到 part 上，首系统全名、之后缩写 → `<part-name>` / `<part-abbreviation>`。
- **中文歌词的起锚**：一页里没有连字符、没有延长线时，自校准那道补锚没有种子，整页歌词全丢（p1）。
  「一个汉字（可带句读）一段、同字体同字号同基线成排三段以上、在某行谱下方」本身就是锚。
- **挡在歌词外的三样**：谱表左边的声部缩写（第二个系统起的「A.」）；页脚（最后一行谱以下、整句汉字、正上方那行谱在它的横向范围里没有符头
  ——光凭「末行谱以下两字以上」会挡掉赞美之泉印在末行谱下的成段歌词）；表情术语只在自校准那一路挡，延长线那一路只改判
  「斜体、离下面那行谱比上面近」的（钢琴 `rit.`）。放宽任一条，赞美之泉的配对都会连锁变（汉字占比跨过歌词否决的门槛）。
- **半角标点并回前一个音节**：「祂!」的 `!` 另起一个音节就占掉下一个音，整行错一格。
- **一个升降号只归一个符头**：升号字形高约三格，三度和弦的上一个头也与它纵向交叠（钢琴 m11 `♯C4 E4 G4` 读成 C♯ + E♯）。
  改成右边一格内、纵向交叠的头里中心最近的那个。
- **上下两声部的整小节长音不并回第一声部**：另一层带干的全朝下、长音在它们上方，就是真上声部（钢琴 m2 A4 全音符 + 下声部「休止 F E D」）。
- **真字体的全音符头不并进带干的和弦**（孤头并回那条是给位图路「干没挂上的二分」写的，`#raster` 合成字体照旧并）：钢琴 m16 上声部 D4 全音符。
- **力度、松叶挪到文本层之后挂，按歌词判归属**：人声力度印在自己谱表上方（= 上一行歌词下面）时，原来那条「印在谱表下方属于上面那行」
  把男声的 p、渐强挂到了女低。给了各行歌词下沿时：记号在上一行歌词之下、下方三格内就是一行谱，归下面那行。只矢量路给，位图路（破碎那种版式）不动。
- **补上原来只打标没挂出去的**：松叶（`wedgeSpans` → `attachWedges`）、琶音（一串竖排的 `wiggleTrill`，`takeArpeggios`，不然每个都成了颤音）、
  速度与表情文字（`attachDirectionTexts` → `<words>` / `<metronome>`）、页眉（`vectorPageCredits`，交给位图路那份 `headerCredits` 分类；
  ToUnicode 给的康熙部首「⾸ ⽼ ⽤」折回正常汉字）。

GT 是以识别稿为底、对原图逐小节核过的（旧的人工抄录本有一处音错：女低 m1 是 D E D）。

### 符杠 / 符尾、弧方向、速度一条、人声方括号（2026-10-08）

识别稿与 GT 原先都缺这四样（GT 以识别稿为底，识别不写 GT 也就没有）。toxml 是矢量路与位图路共用的，两路一起写出。

- **`<beam>` 分开符杠与符尾**（`notedata.ts::beamStates`）：只给接在杠上的干写，挂符尾的八分不写——MusicXML 里不带 `<beam>` 的短音就画符尾。
  逐层（`calcBeamLevels` 定的层号，同层拆成两段的并看）看这一层的杠伸出干的左右（超过端点容差五分之一格）：两侧 continue、只右 begin、只左 end；
  只接上这一根干、短于 1.6 格的是钩（forward / backward hook），长的是另一头的音没认出来，照普通杠算。
  和弦只在写出时打头那个音上写（`emitVoices` 把整枚和弦的杠挪到它身上）。宣主荣耀 40 个，逐个对原图过。
- **弧方向**：`SlurArc.above` 记到起端音上，圆滑线写 `placement="above|below"`、连音线写 `orientation="over|under"`（读入端两个都认；
  `model/toxml.ts` 原来写回 `<tied>` 时丢方向，已补）。位图路和弦连音线那一处（`recognize.ts` 的 `chordTies`）没有弧可看，不写。
- **速度文字合成一条**（`textanalyze.ts::attachDirectionTexts`）：文字层里「Andante」（正文字体）与「q = c 76」（EngraverText）是两段，
  原来各挂各的，成了两个 `<direction>`，钢琴那份还落到不同的音上。先把纵向交叠、横向间隙三格以内的速度段从左到右并成一条、挂在最左那段的音上；
  有节拍器的，前面的文字进 `tempoText`，与节拍器写进同一个 `<direction>`（两个 `<direction-type>`，读入端收进 `Direction.more`）；文字末尾留一个空格（`<words>Andante </words>`），排出来不与音符字形贴住。
  EngraverText 的「c.」字形文字层只吐出一个 `c`，照谱面写成 `<per-minute>c. 76</per-minute>`（`<sound tempo>` 仍是 76）。位图路一行里同时读出文字与节拍器的同此。
- **人声方括号**：Finale 把它画成一笔粗竖带上下两个弯钩的填充曲线，**骑在系统线上**（pt 101.5–109.8，系统线 104.5）。花括号那条要求贴在系统线左边，
  它过不了，接着被弧的「又宽又扁」闸丢掉。判据：高 ≥ 宽三倍、宽 ≤ 2.5 格、与系统线横向相交、纵向罩住两行以上谱 → `PartBracket`
  （不用 `SysBracket`：位图路那个是系统线占位，还有按墨补出来的，拿来分组会误报）。`score.ts::groupParts` 逐系统看括号罩住哪几个声部的全部谱行，
  连着两个以上的记一组；小节线是否穿过组内相邻两行之间的空白定 `<group-barline>`（本曲人声三行的小节线是贯通的 → yes）。
  part-list 里出 `<part-group type="start"><group-symbol>bracket</group-symbol>…` 与对应的 `stop`。钢琴花括号由一个两谱表的 part 自带，不另写组。
- stem 方向原本就写（`<stem>`），GT 里只有 36 个全音符没有，不用改。

## 矢量 GT 的覆盖审计（`../dev/scripts/vector-gt-audit.mjs`）

矢量谱的 GT 以识别稿为底手修，**识别没认领的对象手修时看不见**，就一直漏在 GT 外面。牵我的手初稿审出来的：排练号（7 个，带方框）、
弓法（上弓 1、下弓 4，Maestro 码位 130/131，字形字典里没有）、拍号 ¢ 写成了普通 2/2、人声力度 5 个、`sul G / sul A`、
合成器音色名、每页页脚（版权四行 + 页码，10 页）、声部缩写 W / M、小节号。光看识别侧的 `unknownObjs` 不够：
认领了不等于写出了（页脚打了 TextFrame 标签不进 XML），没认领也不等于 GT 没有（符杠、画成路径的符尾、整小节休止的横杠都没打标签）。
所以审计**不信识别的结论**，只借它的谱表、系统、小节线定位，类别按字形与几何自己判。

- **对账单位**：GT 的系统划分照 `<print new-system/new-page>` 与 `<staff-details print-object>`（`chorus-gt.mjs::gtSystems`），PDF 按页序自上而下，
  两边逐系统、逐谱行、逐小节一一对应——系统数、谱行数、小节数对不上先报「版式」。
  符头、休止、附点、临时记号、弧、力度、松叶、弓法、延长号、连音、琶音按「谱行 × 小节」比个数；文字、和弦、排练号、速度按「系统 × 小节」比；
  页眉页脚按页比 `<credit page>` 的文字；乐器名逐系统比 part-name（首系统）/ part-abbreviation；拍号连 `symbol`（¢ / C）一起比。
- **两边判法不一的地方抵掉**：弧按左端落小节、力度印在小节线前、两行谱之间的松叶挂哪行，两边可以差一格。同系统同类同值里
  谱行、小节各差至多一的一多一少相抵。
- **重描**：Finale 一条弧常画两遍（填充、描边各一个对象，外框差零点几），同类且互相覆盖八成以上算一个。
- **几处字形 / 几何的分辨**：跨行的弧（谱面两截）与 GT 的一对 start/stop 照「起点所在系统一截、后面每个系统各一截」算；
  三连音括号的左右两截会被识别当成松叶（`slur.ts` 的 Wedge 标签），贴着连音数字、与数字同高的短段剔掉；
  渐强、渐弱看两条线在左右两端的张口；竖排一串 `wiggleTrill` 是一个琶音；数字拍号分子分母两个字形算一个；
  页眉一行常分几次 showText 印（「Arranged by」+「Ricardo Chan」），同一行挨着的拼成一行，页码不拼。
- **GT 自身的配对**也查：slur / tied / tuplet / wedge 的 start 没 stop、stop 没 start、未合上又来 start。
  牵我的手初稿里连音组每个音都写了 `<tuplet type="start"/>`——这是写出端 `toxml.ts` 的老毛病（见待办），从识别稿起的 GT 都会带上。

**新增矢量 GT 谱例**：识别稿 → `vector-gt-audit.mjs --one=曲名 --v --crops`（差异处整小节裁图到 `dev/data/vector-gt-audit/曲名/`，
红框是这一组的 PDF 对象）→ 对图改 GT（`--dump=wedge,dyn` 逐条列两边各落在哪、小节内的相对位置；`--patch` 给文字类缺口出 XML 片段）→ 审计归零。
「未识别」不许留：看图后要么在脚本里补判据，要么补 `EXTRA_GLYPHS`（字形字典里没有的音乐字形）。

### 几处**量错了的**指标（都在读 GT 那一侧）

**先确认 GT 读对了，再改识别。** 这类错会把识别的账算到不存在的问题上。

- `xmlStaffTypes` 读 GT 时值的正则是 `<type>([a-z\-]+)</type>`，**不含数字**，
  于是 GT 里所有 `16th`/`32nd` 都读成 `?`，白白记成 516 处时值错。
  改成 `[a-z0-9\-]+` 之后同一份识别结果的时值错项从 1318 掉到 790。
- `xmlMeasureCount` 还要**把不可见小节线并回去**：GT 为排版把一个小节切成两半时，
  前一半的右端写 `<bar-style>none</bar-style>`（全书 141 处），谱面上那一笔根本没画。
  不并的话逐首对上只有 68/84，并了之后 71/84。同一个 `none` 也不能算进
  「结构性小节线」（`gtRepeats`）——它让 GT 那一侧凭空多出 18 根、
  记成一堆「识别漏掉的结构线」。
- `xmlMeasureCount` 数 `<measure\b`，`\b` 在 **`<measure-numbering>`**（`<print>` 里的）
  前面也成立，于是每首歌白白多出一个小节——**全书 64/77 首那个整齐的「小节数差 −1」
  全是这一条**，识别侧根本没错。改成 `<measure[ >]` 之后逐首对上的从 2/77 跳到 65/77。
  同一个坑还有 `<part\b`（`<part-list>` 也命中）与文档里早就记下的 `<note\b`（`<note-size>`）
  ——**这个文件里凡是数 XML 元素的正则，一律写 `<name[ >]`**。
- 整小节休止（`<rest measure="yes"/>`）在 GT 里**没有 `<type>`**（全书 24 处），
  记成 `?` 就凭空多出 24 处时值差异；按常规补成 `whole`。
- 四个逐音序列函数（`xmlStaffNotes`/`xmlStaffPitches`/`xmlStaffTypes`/`xmlSlurMarks`）
  原来**照收 `<chord/>` 附音**，而识别侧一直只取主音——单边多算。
  这个不对称被 `markChords` 漏认二度和弦掩盖着，和弦层改成按符干归就现形了
  （071 一首差 12 个音）。**两边一律只比主音序列**；倚音同理，
  GT 早就跳过 `<grace/>`，识别侧补上 `!n.grace`。
