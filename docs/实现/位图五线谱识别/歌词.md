# 歌词（位图五线谱识别）

> [位图五线谱识别](../位图五线谱识别.md)的分篇。

## 歌词：切字格 → 整行 OCR → 挂音符

扫描件缓存用 `node ../dev/scripts/gen-rasterlyrics.mjs --scan` 补齐（先构建网页与 CLI），
默认仍只生成干净位图缓存。生成与评测都要加载同一份符号模板，否则认领差异会改变歌词条指纹。
缓存仅来自歌词条像素的 OCR，不从 GT 填答案。

GT 评测共用 `node-harness.mjs::xmlLyricVerses`：除数字段号、缺省第一段外，
还识别 Sibelius 的 `partNverse1`。`<lyric-font>` 和 `<lyric-language>` 不能当作 `<lyric>`。
这曾让三份《望十架》静默漏出歌词统计；回归见 `node ../dev/scripts/xml-lyrics-check.mjs`。
仍按第一段中文词对拍，英文版不能当作同语言准确率样本；汇总需同时看配对覆盖。

位图没有文字层，歌词字要 OCR 出来。三步：

1. **切歌词带与字格**（`lyric.ts`，思路照简谱那条路的 `src/omr/lyrics.ts`）：
   每个谱行下方一条带（本行下缘 → 下一行上缘）；带内按**块的纵向中心**分 verse 行
   （不能按包围盒重叠判——「一」那种只有一横的字与相邻字纵向不重叠，会被分到别行去）；
   行内按 x 邻近把块并成字格（**汉字常由多个偏旁连通块组成**，这一步不能省，
   复用 `src/omr/lyrics.ts::mergeToChars`）。
   带里先把**音乐符号剔掉**（符头与查得到音乐字典的），否则谱表内的符号会混进来。

2. **整行送 OCR，不逐格送**：PP-OCR 的 rec 是序列模型，一整条歌词的上下文能把
   单字认不准的救回来；`recognizeTextsPos` 顺带给出每个字在条内的 x，按 x 映回字格。

3. **合成文本对象**（`font: "#ocr"`）交给 `buildLyricLines` / `attachLyrics`——那两步原样跑。
   **不走 `analyzeText`**：那一步靠「带连字符的音节」「音节间的延长线」当锚点认歌词，
   中文逐字一个音节、既不连字也不拉线，一整行一个锚点都没有。位图这边本来就是
   **按位置**切出歌词带的，身份已经确定，不必再认。

### 断行要按**间隙**，不能用定宽窗口——这是歌词档最大的一个洞

`splitRows` 原来的判据是「块的纵向中心离**本行第一个块**不超过 0.9 格算同一行」。
一行歌词里各块的中心本来就散得开——「宀」的头在上、「，」在下、「一」在中间，
字高又常有 1.2 格，整行的中心跨度轻松超过 0.9 格。于是**同一行歌词被劈成两行**，
两边各拿到半拉偏旁，OCR 出来是同一句词的两个残本：

```
（宁静 p3，改之前）
谱行#5  格4   f1寧靜的
谱行#5  格9   y1.寧静的伯利          ← 与上一条是同一行词
谱行#9  格13  安的夜已深.郊外有一群
谱行#9  格12  恆，平安的夜已深。郊外有一群牧羊人，   ← 同上
```

两条都挂到同一个谱行上，成了 verse 1 与 verse 2，字格宽度也全是碎片
（一行里既有 5px 的残片又有 37px 的两字连体）。

改成**相邻两个中心拉开一段空白才断行**（`ROW_GAP`，按线距算）：

| | 歌词（产物档） | 歌词（按 staff） | 宁静 | 破碎 |
|---|---|---|---|---|
| 定宽窗口 0.9 格 | 44.2% | 53.2% | 66.3% | 40.1% |
| **按间隙断行** | **64.9%** | **71.3%** | **82.4%** | **59.9%** |

门槛扫过 0.45 / 0.6 / 0.75 / 0.9 / 1.1 / 1.4：71.14 / 71.19 / 71.34 / 71.34 /
71.34 / 71.39%——0.75 往上是一整片平台，取中间的 **0.9**。再往上会把相邻两段词
并成一行（两段的中心差约 1.5 格），平台就到头了。音符各档纹丝不动。

> **拿「全页字宽」去剔假字格，两条都试过，都是净亏。**
> 汉字等宽，本以为能砍掉混进歌词带的非歌词墨块（弧线端头、符干尾、简谱数字）：
> ① 宽度闸（丢掉 `w` 不在 0.55~1.7 字宽的格）：歌词 71.3% → **67.2%**；
> ② 中心 y 对齐闸（丢掉偏离行中位数超过 0.35 字高的格）：71.3% → **65.6%**。
> 原因是同一个字的偏旁**并不总能并成一格**，按宽度或对齐去砍，砍掉的多是真字的一半；
> 而整行送 OCR 时那些碎片有上下文兜着，本来就认得回来。
> 全页字宽仍然留着——用来把**字号**量准（只拿宽度接近一个字的格去量字高，
> 逐行那个初值是偏旁块高，偏小）。

### 字符映回字格：字数相同按序号，否则**单调对齐**（不是各取最近）

字数与字格数相同时按序号一一对应，这一条最稳。**不同的时候原来是「逐字各取最近的格」**
——那是错的：字与格的次序本来是一样的（都是从左到右的一句词），
各取最近会**乱序**（两个字抢同一格时后一个直接丢掉，而它本该落在下一格里）。

改成一趟 DP 的**单调对齐**：保序地把字摊到格上，允许跳过空格（字少于格）、
也允许丢字（字多于格，多半是 OCR 多读了一个，`DROP_COST` 0.08 比摊到最近的格贵一点
——宁可丢，也别把整句往后顶）。

### 标点并进相邻的字，不另占一个格

「，」「。」自成一格会**占掉一个音符的位置**，整句词往后错一个音。
所以字符这一侧照简谱路 `omr/lyrics.ts` 的口径折：尾随标点（，。、；：！？…—”’））
并进前一个字，开引号（“‘（）领起后一个字。一个字格于是拿到「字 + 尾随标点」。

| | 歌词（产物档） | 歌词（按 staff） |
|---|---|---|
| 各取最近 + 标点自成一格（原来） | 64.93% | 71.34% |
| 单调对齐 | 67.22% | 73.53% |
| **单调对齐 + 标点并前** | **67.67%** | **73.99%** |

> **「按全页字宽切方块字格」试过，净亏 3 个点。** 汉字等宽，本以为可以拿字宽当尺子
> 把粘连的两三个字等分开（`mergeToChars` 只按间隙并，粘连字并成一格，
> 字格数与 OCR 字数对不上）。结构指标确实好了——每行「字格数与字数之差」的平均
> 从 3.73 降到 **1.08**（字宽取全页块高的 85 分位数，间隙 0.35 字宽、
> 超过 1.75 字宽才等分；这几个门槛都扫过），可歌词档反而掉：
> **新格 67.67% → 64.56%**（按 staff 73.99% → 71.02%）。
> 等分的切点是估的，落在字里的时候「按序号一一对应」那条准路会整句错位，
> 比格数多几个、由单调对齐去摊还要糟。**字宽仍然留着**——量字高要用它挑
> 「宽度接近一个字」的格（块高的中位数是偏旁的高度，偏小）。

**不能要求「`xFrac` 落在字格区间内」**——那是 CTC 估出来的位置，误差常有半个字，
实测那样会丢掉近一半的字（1221 个里丢 566）。

### **不做形状聚类，直接用 OCR 的文本**

试过「字格 → 32×32 签名聚类 → 每类投票定字」（照 `gen-staffocr.mjs` 的每类只送一次
OCR 的账），**净损耗**：5985 个字格聚成 1866 类，只定下 969 类、覆盖 52%，歌词 35%。
门槛往松扫更差（把不同的字并成一类，票散开、过不了半：覆盖 44.6% / 32.9%），
往紧扫也只到 58.7% 覆盖。直接用 OCR 文本，宁静一首歌词 53.2% → **58.2%**。

> **量歌词档之前，必须先把缓存跑全**（`node ../dev/scripts/gen-rasterlyrics.mjs`）。
> 缓存是**按条的内容指纹**寻址的，任何动到 blob 抽取的改动都会让指纹变、缓存落空
> ——那一条就成了空歌词，歌词档假跌。反过来，缓存**不全**时也会假涨：
> 没命中的条不注入任何字，而 `acc` 对「多出来的字」是要扣分的。
> 实测在提交状态上补全缓存（新增 271 条**都是真歌词**），
> 破碎的歌词从 33.6% 掉到 22.2%、全语料 50.0% → 44.2%
> ——**掉的那一截不是退化，是原先虚高**：认出来的歌词多了，
> `attachLyrics` 把一部分挂到了错的谱行上，这才是真实水平。
> 线上没有缓存、每条都现跑 OCR，等价于缓存跑全的状态。
>
> 判断改动时：动了 blob 抽取就先重跑缓存，再看歌词；不然只看音符/音级/小节自检。

缓存按**条的内容指纹**寻址（`stripKey`，FNV-1a），不按「第几页第几行」：
几何判据一动行的编号就全变了，按位置存的缓存整份作废；按内容存的只要那一条的
像素没变就还能用。命中缓存时识别仍然不起浏览器。

**只收汉字与全角标点**：PP-OCR 认不出时会吐拉丁字母或占位符，收进来就成了歌词里
凭空多出的字（实测 `l` 一个就出现二十几次）。查不到字的格**留空**，不编造。

### 归行与编段号：**一条就是一行，段号按文种分开编**

- **`buildLyricLines` 归行，合成对象要纵向重叠过半才并**（`#` 打头的字体）。原来擦边就并：
  行距窄的中文段上下两条的盒互相压着十来个像素（标点、偏旁出头），三段词并成一段、按 x 交错
  （《倚靠主永远膀臂》「遠膀臂；何我每日满等有…」）。位图这边一条歌词条本来就是一行。
- **`splitTall` 谷底门槛 0.3 → 0.35**：中文段行距只隔半个字高时谷底是峰值的三成出头（倚靠主 0.315），
  扫过 0.25~0.45，见 `lyric.ts::TALL_VALLEY`。
- **段号按文种分开编**（`recognize.ts::numberVersesByScript` / `settleLyricVerses`）：每行谱下按上下次序，
  汉字行编 1、2、3…，拉丁行先占位 `100 + k`，整首汇总时挪到「全曲中文段数 + k」。
  副歌只印一次的中英对照谱，副歌那几行谱下只有一行中文一行英文，原来连着编，英文副歌成了第 2 段、
  落进中文第 2 段（整段归零）。GT 照 MusicXML 通行约定：副歌记在第 1 段、英文副歌记在英文第 1 段。
  全曲中文段数要**整首**定（《倚靠主》第二页只有副歌），所以分两步；调用方（harness）在 `buildScore` 前调
  `settleLyricVerses`。零星几个字的段（字数不到最多那段两成）不计入中文段数——《我灵镇静》一条只认出
  「夏：」的假行曾让英文整体后移一段。六首副歌曲子起来，独唱谱中文 88.32 → 93.06%、拉丁 84.69 → 92.87%。
- **英文副歌归英文段**（三处配合）：
  1. **中英混在一条的切成两份**（`lyric.ts::splitMixedChars`）：按 OCR 字的 `xFrac` 分文种连续段，够格的拉丁段
     （≥5 个字母，带连字符或 ≥12 个字母）单独成一个拉丁对象，汉字那份的字格避开它（`stripWithout`）。
     《信心使我得胜》「歡呼聲迴響應。Faith is the vic-to-ry!」、《倚靠主》「倚靠主耶穌永遠膀臂。Lean-ing,」。
     `buildLyricLines` 里文种不同的合成对象不并成一行。
  2. **段号按「上方同文种、横向盖得住的行数 + 1」**：英文副歌印在右半边，左边主歌英文段盖不着它，就是英文第 1 段。
     还**按音节**数：一行里有一截伸出上方各行范围（多于一个音节宽）的，拆出去单独编号
     （倚靠主低音谱表下第 2 行「…arms. Lean-ing on Je-sus,」后半是呼应句；数算主恩第 3 段行尾「…見天父．主的恩典，樣樣」
     是副歌起句）。拉丁行要连着 ≥3 个音节；汉字行 ≥2 个，另有两道闸——末段后的「阿们」不拆（唱完末段才唱，GT 记末段；
     不拦时万古磐石歌、救主降生等七首各掉 1~3 点），行首那一截要以句末标点收尾（是谁「你。是你，主耶穌，唯有你。」；
     各段字数不同的曲子行首本来就参差，耶和华是我的牧者「我擺設筵」「隨着」拆了 96.2 → 90.9%）。
  3. **链进来的拉丁行字母下限 8**（`LATIN_MIN_CHAINED`，原来也要 20 个）：信心使我得胜第二页英文第 3 段
     「And ech-o with our shout.」17 个字母整行丢了，第 4 段顶上来。
  信心使我得胜拉丁 92.5 → 97.1%，合计拉丁 92.87 → 93.37%。
  4. **呼应句改挂下一行谱**（`recognize.ts::moveEchoLines`）：倚靠主高音唱长音「倚——靠」、低音接「倚靠主耶穌」，
     低音的词印在两谱表之间主歌各行下面，被当成高音的第 2 段。逐音节比到两行谱最近音的距离：同一行谱下，
     上面先有一行跟着上一行谱走（明显离下一行谱更近的 ≤0.15），它下面出现明显离下一行谱更近的（≥0.5、离上一行谱更近的 ≤0.1），
     从那一行起往下都改挂下一行谱。**要有对比**：耶和华是我的牧者一行谱下三段全都偏向低音（0.40~0.69，高音的音认漏了），
     只看单行就挪，中文 96 → 45%。倚靠主中文 73.6 → 86.2%、拉丁 78.1 → 85.3%。
  5. **`attachLyrics` 越过同 x 的音**（`staffomr/textanalyze.ts`，矢量路共用、staff-diff 不动）：原来往后找「更近的音」，
     碰到和弦里同 x 的两个声部距离相等就停，从行中间起头的一截（上面拆出来的副歌起句）整串卡在第一个音上。
- **GT 约定：副歌只印一次的，副歌记第 1 段，英文副歌记英文第 1 段**（用户认可修 GT）。
  是谁、以马内利来临歌、你的信实广大三份原先照印记在第 2 段，已改成第 1 段（`dev/data/五线谱/gt-src/`，只动 `<lyric number>`）；
  数算主恩、更亲近恩主、信心使我得胜、倚靠主本来就这样记。
  `LATIN_FRAC` 降到 0.8（让混排条整条按拉丁走）试过：倚靠主涨、信心使我得胜跌，改走切分。
### 逐首补的几处

- **彩色页的歌词条送灰度 OCR**（`RasterPage.lyricGray`，`stripOf` 裁一份 `gray`，`stripKey` 有灰度按灰度算、前缀 `g`）：
  二值化、去网把细笔画一起吃了——坚固保障（网点 0.36）英文字高 14px，「mighty」在条子里只剩几截残笔，
  原图清清楚楚。中文 80.7 → 99.2%、拉丁 85.5 → 99.4%。先只给去过网的页，放开到全部彩色页再净涨 0.2；
  合唱谱扫描件歌词 65.53 → 65.70。`data` 仍是二值，量词界用。
- **字比格多时补格**（`fillMissingCells`）：字格只来自没人认领的块，字的块被别的识别器认领走了（所信有根基粗体大字），
  OCR 照样读得出、格里却没有，对齐时丢字。OCR 字左右 0.3 个字宽内一个格都没有的，按字宽补一个。
  主使我喜乐 90.6 → 98.8%、我一生要赞美你 83.9 → 94.6%、齐来崇拜 86.2 → 91.1%，没有掉的。
- **`splitTall` 的「太高」按块高 85 分位**（整字高）量，不按中位数（偏旁高）：大字本一行行都「太高」，
  在偏旁之间找得到谷，一行的上半截被劈出去。奇异恩典拉丁 89.8 → 98.5%、来敬拜荣耀王 86.9 → 91.7%。
- **切不开的高行按横向大空白分块再切**（`splitTallByColumns`）：信心使我得胜第二页主歌在左、中文副歌在右落在第 2 段高度，
  两行之间的谷只有峰值一半。分块切完、纵向重叠过半的横向并回（没切开的块会把一行碎成并排几条）。
  整条歌词带一律先分块试过：长音底下各段一起留白很常见，一切就碎，中文 −4.6、拉丁 −15。
- **末行谱下的带要一行接一行**（`TAIL_FIRST` 6 格）：信心使我得胜谱末 8.5 格处的经文「我倚靠神……詩篇五十六篇」
  字号与歌词一样，被收成第 1、2 段。真歌词第一行离谱表 1.8~3.3 格。信心使我得胜中文 83.5 → 98.8%。
- **行首段落标记「(歌)」「（副歌）」不收**（`dropSectionLabel`）。
- **拉丁行链入的上下距离 2.5 → 3 个字高**（`LATIN_CHAIN`）：拉丁行的字高常只量到小写字母高（更亲近恩主 12px、行距 34px），
  末段后半「heights of joy…」没连字符又链不进来。更亲近恩主拉丁 89.4 → 98.8%，3 与 3.5 一样，别首不动。
- **拉丁行链入的字高比 0.8 → 0.75**：父恩广大末系统英文第 1 行没连字符、字高 20 对邻行 26，链不进来，英文 2~4 段整体前移，
  拉丁 69.4 → 94.3%。晨曦破晓末行下的版权行照样挡在外面。
- **试过撤掉的**：`splitRows` 之后「纵向大半重叠的相邻两行并回」「薄条（矮于邻行 0.6）并回」两种，一个不起作用、
  一个伤了向主唱新歌（100 → 63.6%）与音符。所信有根基末行谱下那条「世世中世日光北」（一行字的上半截偏旁）仍在。

### 夹在两行谱之间的歌词归哪一行（`buildLyricLines` 的 `pickBelow`，位图路）

默认一行歌词归它上方最近的那行谱。有的声部把词印在谱表上方（望十架：p3 独唱声部；页底那行词其实是下一系统顶行的，挂到了上一系统的钢琴左手上）。
位图路给 `buildLyricLines` 一个判据（`recognize.ts::lyricsBelongBelow`），矢量路不传，判据一个不变。

**照简谱夹在两行数字之间的八度点那套判**（[OMR-简谱识别](../OMR-简谱识别.md)「两声部一组裁决夹在中间的八度点」）：
不按远近，也不比总的对位率，先看互斥，再看排除性证据，定不下来照原样。

1. **互斥**（对应「下声部脚下已有点的，这颗归上声部」）：
   - 下方那行谱是单声部、自己下面已经有词（它与再下一行谱之间离它最近的就是它），这一行归上方（破碎 p8 女低那行词有几处女低休止、
     男高有音，按证据挪去了男高，整行 27 字）。两声部一行的谱上下可以各挂一行（各归一个声部），不算；
   - 上方那行谱与这一行之间已有它自己的汉字行，这一行是那串多段歌词往下接的一段，归上方（万古磐石歌第 4 段离下一系统近、
     下一系统两声部，挪了过去，中文 100 → 75%）。
2. **排除性证据**：逐音节看对不对得上两边的音（x 差 0.9 格以内），**两边都对得上的不表态**——SATB 上下两行节奏一样，证据为零，照默认。
   只对得上下方的至少 3 个（`LYRIC_ONLY_MIN`）、是只对得上上方的 2 倍（`LYRIC_ONLY_RATIO`），下方又一音一字对得上六成，才挂下方。
   原来按总对位率比（下方高三成就挪），要靠「至少 8 个音节」挡住上方那行恰好在几处休止的短行（烛光颂曲 p5 一行六个字，上 0.67、下 1.00，
   只对得上下方的只有两个）；按排除性证据，这一道降到 4 个。
3. **上方没有谱**（页顶那条带）：没有别的主，可那里也有标题、诗歌编号、署名、速度语。三条：
   - **段号是歌词的强判据**：行首印着一位数段号（「1.」「2、」，OCR 读出来、折叠时剔掉，`verseObjs` 记一笔），免掉下面的字距，
     一音一字对上六成就挂。只认一位数：页顶标题前的诗歌编号也是「数字 + 点」（有一位神「23.有一位神」）；
   - **字距**：标题、署名字挨着字排，相邻音节中心距的中位数约一个字号；歌词跟着音符排开，要 ≥ 1.5 个字号（`LYRIC_PITCH_MIN`）
     ——署名「刘福群 何统雄译」1.0。字号取各音节字格**长边**的 85 分位（同 `lyric.ts` 量字宽）：大字号的标题整字比歌词字号上限高，
     进不了歌词带，只剩碎笔当字格（我一生要赞美你页顶标题「一」只剩一横、高 3 像素，按字格高量出 3.3 倍；碎笔长短不一，
     中位数也只有 44、真字 83）；
   - **大部分一音一字**：按 x 从左到右，每个音节配最近、还没配过的那一拍（同一列的和弦成员算一拍），配上八成（`LYRIC_HEAD_FIT`）。
     只看「附近有没有音」的话，一个音能被前后几个字都算上。标题碰巧对得上的不少（你的信实广大 5/7 = 0.71、我一生要赞美你 6/6），
     字距与一音一字两道一起才挡得住；望十架 p3 页顶那行歌词 0.93、字距 2.0。

- **只判汉字行**：拉丁行按词切，词中心落在几个音中间，对位比不出来（坚固保障拉丁段被挪走，拉丁 99.4% → 38%）。
- **上方的谱只要有就交出去**：多段歌词后几段离谱远、靠链式接上（`chainGap`），也是上方那行的；当成「上方没有谱」，
  独唱谱五首的后几段被挪到下一行（善牧恩慈歌中文 100% → 18%）。
- **页顶那行谱上方也切一条带**（`lyric.ts::findLyricRows` 的 `i = -1`）：歌词带原来只在每行谱下方找，页顶第一系统上方的词
  （望十架 p3 独唱声部）连条都没切出来。从页顶那行谱的上缘往上 `HEAD_BAND`（14）格，从谱表往上一行接一行收
  （最近一行离谱表不过 `HEAD_FIRST`（6）格，再往上每行与下一行的间隔不过下一行高——同末行谱下面那条带）。
  切出来的行没有上方的谱，挂不挂全交给上面这条判据：对不上的（标题、速度、表情记号）没人要，留在账本上当歌词墨。
  新条要补 OCR 缓存（`gen-rasterlyrics`）。

读数：望十架歌词操作 62 → 22 步（`chorus-ops.mjs`）。

### 一行谱两个声部、上下各印一行词：各归哪个声部（`recognize.ts::splitVoiceLyrics`）

望十架独唱与女低共用一行谱：独唱的词印在谱表上方（上面那条挂过来的）、女低的印在下方。不分的话两行词按 x 挂到同一串音上，
下方那行成了上声部的第 2 段，下声部一个字也没有；GT 是两个声部各一段中文。

同上，**不按上下位置定，按排除性证据定**：逐音节数「只对得上第一声部的音」与「只对得上其余声部的音」（两个声部同一拍都有音的不表态），
比「上方那行归第一声部、下方归其余」与「反过来」两种分法哪种证据多；**一个声部同一处不会挂两行同文种的词**（互斥），
一行定了另一行就是另一个声部。证据至少 3 个、是另一种分法的 2 倍才分（`LyricLine.voice`，`attachLyrics` 按它筛音；
段号各声部各编，`numberVersesByScript` 按「谱行 × 声部」分组），否则照原样（两行当同一串音的两段词）。
只拿汉字行算证据，同一侧的拉丁行跟着同侧的汉字行走。挂得对不对还要看声部本身分没分对（望十架 p3 下声部的音多半没认出来）。

### 挂位：字挂在哪个音上

测评两侧先按拍位展开（`xmlByOnset`），同一拍的几个音从高到低排；挂位档比的是逐音「有没有挂这一段的字」。
诊断用「按音高对齐音符，再比对上的音有没有字」（拍位钥匙太严，识别侧时值一有出入就对不上）。

- **字挂到同一拍最上面的音**（`recognize.ts::liftLyrics`）：`attachLyrics` 只按 x 找最近的音，同一 x 上几个和弦成员
  谁排在前面就给谁，常落在女低 / 和弦下方音上（万福泉源歌第 1 段每个字都挂在 E4、GT 在 G4），每个字错开一位。
  同一行谱、x 差不到半格、时值相同、其中一个是和弦附音的，挪到最高那个音。两道闸：
  这行谱和弦附音占主音三成以上（闭合谱）；**三行谱以上的系统不挪**（合唱谱一个声部一行谱，同 x 更高的「和弦成员」
  多是多认出来的假头：破碎女高那行 C5 上叠出 F5，挪上去女高、女低歌词 98 → 96、97 → 94%；按「三行以上挂歌词」判不够，
  扫描件望十架只在最上面一行认出了歌词）。只在同一行谱里挪，女高女低分在两行的不会互相挪。
- **一个和弦只挂一个音节**（`attachLyrics` 的 `sameCol`，位图路传 0.3 格，矢量路默认 0 不变）：挂完一个音节原来只往后挪一个音，
  下一个音节常落到同一和弦的另一个成员上，两个音节挤在同一拍，展开后次序颠倒。中文也大涨：
  万口欢唱 91.5 → 98.6%、我灵镇静 92.8 → 99.4%、父恩广大 89.7 → 92.3%、所信有根基 80 → 85%，独唱谱中文 96.99 → 97.68%；
  合唱谱扫描件歌词 65.70 → 66.10%。倚靠主副歌一呼一应那段（高低音两行谱同一段词交错）两档各掉 1~2 点。
- **试过撤掉的**：英文断词门槛按每条字距自适应（空白游程中位数 × 2.5，夹在 0.4~0.7 个字号）——《我灵镇静》
  「Be still, my」字母间 1~3px、词距 15~16px，字号 27px 的 0.7 倍 19px 把三个词连成一个音节。挂位 +0.28，
  但信心使我得胜、大地风光、坚固保障把词劈开、音节多过音符，拉丁 −0.56，不划算。

## 歌词条的 OCR 缓存：**生成器必须与识别走同一条路**

`gen-rasterlyrics.mjs` 原来自己复制了一份流程（另一套 `findStaffLines` / `findBlobs` /
`findLyricRows`）。识别这边一改判据，两边切出来的条就不一样、指纹全变、**缓存整份落空**
——而落空的表现是「歌词档暴跌」，看上去像识别退化（实测 85.0% → 42.7%，查了半天）。

现在条子由 `RasterPageResult.lyricStrips` 从识别里直接出，生成器只管送 OCR。
对齐之后**歌词 85.0% → 95.7%**（按谱行档）——原先那个数是**缓存早就没对上**的虚低，
两边同路才量得准。

## 拉丁歌词：**绕开方块字格**

汉字那一套（`mergeToChars` 按字高并格 → `mapCharsToCells` 把 OCR 的字摊到格上）立在
**汉字等宽见方**这个前提上。英文词宽差着数倍，照搬必错位。
所以拉丁行直接拿 OCR 的 `{ch, xFrac}` 逐字造盒，断词断音节交给矢量路现成的
`splitSyllables`——那一步本来就是给拉丁歌词写的（遇空格断词、遇 `-` 断音节并记下
`hyphen`），一行不改就能用。字格那一层仍然保留：`ledger.claim(cell, "lyric")` 的记账靠它。

### 词界按**条子里真的空白**判，不按 `xFrac` 的间距判

PP-OCR 的 rec **不吐空格**（字表里没有），词界只能自己判。`xFrac` 是 CTC 估的位置，
一个字常差半个字宽，按它判出来的词界一半是错的（实测 `bul-wark nev-er` 判成
`warkney- er`，音节一错位整行就对不上音符）。改成量条子的列投影：连着
**0.7 个字号**没有墨就是一个词界。

这个 0.7 不是排印意义上的词距（0.3~0.5 em）：歌词是**逐音节排在音符下面**的，
词与词之间拉开的是音符间距。实测十二行英文歌词的空白游程中位 2~5px、七成位 7~15px、
九成位 18~35px（字号 13~17px），两头分得很开。按排印词距取 0.28 个字号，整行碎成
单字母（`w orld`、`M an`）。

空白归到哪两个字之间按**空白列的中点**判（中点落在前一字与后一字的 `xFrac` 之间）。原先要整段空白都夹在两字之间，
标点的 `xFrac` 常被 CTC 估到空白里去，句读后的词界整批丢了（Holy, Holy, Holy `ly,ho`、`y!God`、`was,and`，四段共十二处）。
改后独唱谱挂位 95.62 → 95.86%，十二首涨（奇异恩典 94.3 → 99.7、求主同住 92.8 → 97.2）；父恩广大拉丁 99.8 → 98.6、挂位 −0.3，
那首只多切开了两处、两处都对（`mands,I`、`sky,And`），掉分是旁边本来就粘着的词（`arethymer`）让后面的音节整体错了位。

行首的段号连同后面的点剥掉（`dropVerseNumber`，汉字行与拉丁行都过）：数字不是歌词字、会被滤掉，跟着的点却留下来，
领到第一个字前面成了 `.Ho`。

### 判「这是拉丁行」要三道闸，**一道都不能省**

拉丁字母在成字的字符（字母 + 汉字）里占 **≥0.9**、整行字母 **≥20 个**、
并且**至少有一个连字符**。

- 前两道挡 OCR 的垫背字。汉字行只收 CJK，认不出的墨迹吐出来的拉丁字母自然被滤掉；
  拉丁行一开，它们就成了假英文行。只按「过半」判，合唱谱那批的噪声行整片被判成英文
  ——歌词一变，`score.ts::assignSlots` 定谱行身份的「有没有词」跟着变、跨系统连接跟着变，
  **音符档 85.23% → 82.53%、扫描件 67.07% → 62.17%**。
- 第三道挡**页眉页脚与版权行**：那是货真价实的整行英文，前两道拦不住。实测破碎那份
  六页的书眉（`NEWHEARTMUSICMINISTRIES73REVEREYOURGLORY`）与版权行整片被收成歌词，
  扫描件音符档 67.07% → 66.72%。判据是连字符：歌词逐音节排在音符下面
  （`Mas-ter`、`Up-on`、`bul-wark`），一整行下来必带；书眉、版权、脚注一个也没有。
  代价是整行全是单音节词的歌词行会漏掉（实测《主，差遣我》有一行 `take up the cross;`）。

### 顺带修掉的两条

- `splitSyllables` 里那条「整字见方却只读出一个 ASCII 字符 = 这套字体的全角空格」
  **对合成字体不适用**（位图路造的 `#ocr` / `#raster`）。合成对象的盒是按 `xFrac`
  摊出来的，一个拉丁字母的盒轻易就过 0.8 em——实测《坚固保障》四行英文歌词整片被它
  吃掉，一个音节都没剩。
- `buildLyricLines` 收歌词行：**第一段**不过三个谱表高，**后面几段按「接着上一段」收**。
  独唱谱一页能印八段（中文四段 + 英文四段），第五段起就出了三个谱表高，文本对象造得
  好好的却一条也不收；而单把上限放大会让合唱谱多收进页脚。段与段本来就是等距排下来的，
  中间没有空当，页脚离最后一段远得很，链断在那里。
  `rasteromr/lyric.ts::TAIL_BAND`（末行谱下方的歌词带）同步放到 24 个线距。

  **这条链只对合成字体开**（`#` 打头，位图路自己造的文本对象），与上一条认的是同一个记号。
  一开始没加这道闸，矢量路也跟着链——赞美之泉的歌词档从 94.95% 掉到 94.88%，
  连带「同一版」那一档的曲目集合也动了（时值 97.71% → 97.62%）。
  那本每首最多两段，用不上链式；**多收进来的行都是本不该收的**。

  ——改了共用代码，三条守门（`staff-diff` / `chorus-diff` / `staff-measure-all`）要一起跑。
