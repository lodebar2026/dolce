# 度量、跨系统连接与对拍（位图五线谱识别）

> [位图五线谱识别](../位图五线谱识别.md)的分篇。
>
> 本篇的读数与尺子是旧回归 `chorus-diff.mjs` 的（2026-10-06 删去）；现在回归只量手动操作步数（`chorus-ops.mjs`，见总篇「基线一眼」）。
> 手动操作按「识别系统 ↔ GT 段」逐行比、整份算，碎成几条也逃不掉补音的代价，下面「奖励碎片化」那个问题不再存在。

## 跨系统连接：`sameToken` 的两条**通配**，与一把不奖励碎片化的尺子

### 先说尺子：`noteAcc` 会**奖励碎片化**

逐声部对拍是「识别的谱表 ↔ GT 的谱表」贪心配对，**没配上的识别谱表一个音都不付代价**。
跨系统连接一断，一条谱表碎成好几条，配对就能给每个 GT 谱表挑一段最像的
——实测破碎碎成 13 条时 `noteAcc` 64.2%，正确连成 7 条反而 60.9%。
**照这个数调，会一路往碎里调。**

所以另加一档 **`noteAccAll`（含游离）**：把没配上的那些识别谱表里的音记进分母。
一份好的输出应当**每个音都在、且都在对的那一路上**，这个数才量得出跨系统连接。
判连接对不对看它，别看 `noteAcc`。

### 病灶：括号与谱号一时认得出、一时认不出

`StaffToken` 拿「谱号 + 谱表大小 + 在花括号的上半/下半」当一行谱的身份，
`sameToken` 原本要求这四项**全等**。位图路上后两项都不稳：

- **人声组的细括号罩几行随曲子在变**。合唱谱左端除了钢琴大谱表的花括号，
  还画着把人声组括起来的细括号；人声有几行随曲子推进而变（破碎从 1 行长到 5 行）
  ——同一条括号在两个人声的系统里罩两行、被 `findBraces` 的「恰好罩两行」留下，
  到三个人声的系统里罩三行、被丢掉。于是同一条谱行的签名一时是 `T`/`B`、一时什么都没有。
- **谱号偶尔认不出**（宁静 100 行里有 3 行），那三行把一条谱表劈成了两条。

### 修法：**认不出的那一项不参与否决**

```
size 不同        → 不是同一行
谱号两边都认出来了、又不同 → 不是同一行；有一边认不出 → 不拿谱号否决
两边都认出括号、上下半不同 → 不是同一行；有一边没认出 → 不拿括号否决
```

`T` 与 `B` 之间仍然互斥——大谱表的上行不会是下行，那一条是可靠的。

| | 音符 | **含游离** | 宁静谱表 | 破碎谱表 | 游离音符 |
|---|---|---|---|---|---|
| 原来（四项全等） | 67.25% | 62.88% | 10（GT 5） | 13（GT 7） | 323 |
| 括号通配 | 66.30% | 64.14% | 8 | **7** | 124 |
| **括号 + 谱号都通配** | 66.85% | **66.73%** | **6** | **7** | **6** |

`noteAcc` 与歌词档略降，降的正是碎片化那份虚高（破碎的 `noteAccAll` 从 61.0 到 60.9，
纹丝不动，掉的 3.3 个点全是碎着蒙来的）。矢量路各档不动（`sameToken` 是共用的，验过）。

### 两条从 Audiveris 那边印证的

[Audiveris 的 part collation](https://audiveris.github.io/audiveris/_pages/guides/specific/logical_parts/)
把每个系统的物理声部映到全曲的逻辑声部，判据是「谱表数、谱线数、小谱表属性」加声部名，
**次序上以钢琴那个双谱表声部为锚**：在它上面的自下而上配，在它下面的自上而下配，
没有钢琴就一律自下而上。

- 本仓的 `lcsPairs` 从后往前回溯、见相等就配，**等价于自下而上**——与它一致。
  别改成偏好靠前：实测掉到 57.3%（直觉上「新声部加在已有声部下面、所以该配给靠前的」
  是错的）。
- 它也是先把系统内的谱行**按括号归成声部**再配，本仓是逐行配、最后才分声部。
  这一步的差别在本语料上还没显出代价，真要动再说。

### 「一行谱写着两个 GT 声部」——**合流档试过，一次都不成立**

上面那个解释（印谱行少于 GT 声部数，所以一行上写着不止一个声部）听着顺，
但**量不出来**。做法是给 GT 的每个音算出起点（走一遍 `<measure>`/`<backup>`/
`<forward>`，按 `divisions` 归一），把**相邻的**两条 GT 谱表按起点交织成一条
——那就是它们挤在同一行时谱面的次序——再拿识别侧的谱表去配。

三条判据缺一不可，缺了就是拿度量蒙分：

- **只合流相邻的两条**。不限相邻时，度量会挑「凑得最像」的任意两条
  （实测破碎把 P2 与 P4 合流，中间还隔着 P3），合流档虚涨到 65.7%。
- **按总分比，不能只跟两条单配比**。用来合流的那条识别谱表多半已经与别的
  GT 谱表配着了，合流会把那条挤掉——收益要盖过这笔损失，否则是同一条谱表记两次分。
- 挤掉的那条分母还在、分子归零。

诚实记账之后：**破碎一次合流都不成立**（P1+P2 合到我们那条上只有 27.4%，
虽然比两条单配的 15.0% / 17.8% 高，却盖不过被它挤掉的那条 55.2%），
宁静本来就是一对一、零合流。这套机制因此没有留在 `chorus-diff.mjs` 里。

**所以缺口的成因还没定论。** 剩下两条只在七行系统里出现的识别谱表（各 45 个音）
配着 GT 的 294 与 241 音的声部——更像是**版式扩行时同一行的身份变了**
（时间上的多对一），而不是同时写着两个声部。要定论得有一份逐行的对照。

### 度量改口径：**按 staff 比，声部挂接交人工**（`testdata/合唱谱/staffmap.json`）

跨系统连接与识别是两件事，混在一个数里谁涨谁跌都看不清。所以另开一档
**按 staff 对比**：识别侧只交出「第几个系统的第几行」（`gotRows`，不经 `buildScore`），
「哪一行是哪个 GT 谱表」由一份**人工映射**给定，逐 staff 直比，不再贪心配对。

映射按**系统的谱行数**分类——同一首曲子里人声陆续进来，系统的行数从 2 变到 7，
而**行数一样的系统各行的身份也一样**（破碎、宁静都成立），所以一首曲子只要几行：

```json
"破碎/S014320OC.pdf": { "byRowCount": {
  "2": ["P6.1", "P6.2"],                                   // 只有钢琴
  "5": ["P1.1", "P4.1", "P5.1", "P6.1", "P6.2"],           // Soprano/Alto/Men + 钢琴
  "7": ["P1.1","P2.1","P3.1","P4.1","P5.1","P6.1","P6.2"]  // 三个女高 + 女低 + 男低 + 钢琴
} }
```

`null` = 这一行不入分母；`"systems"` 可按系统序号覆盖。`--genmap` 出草稿
（每一类里把「第 k 行」跨系统连起来，与 GT 贪心配一次），**再照谱面的声部标签手改**
——草稿在 2 行、3 行那几类上是错的（音太少，配到谁都像）。

| | 音符 | 音级 | 歌词 |
|---|---|---|---|
| 旧口径（`buildScore` + 贪心配对） | 68.1% | 69.1% | 64.9% |
| **按 staff（人工映射）** | **71.0%** | **72.2%** | **71.3%** |

差的那几个点全是跨系统连接吃掉的。逐 staff 一摊开，病灶各归各位：

- 宁静 P4.1（钢琴右手）**56.2%**，读错 137 —— 全曲最大的一个洞，是识别的活。
- 破碎 P1.1 **33.2%**（多出 106）、P3.1 **29.0%**（漏 245）—— 这两个不是识别的错：
  五行系统里三个女高**合印成一行 "Soprano"**，那一行按映射记给了 P1，
  P2/P3 就只剩七行系统里的那一段。

> **「一行罩着好几个 GT 谱表」试过，更差。** 映射支持写 `"P1.1|P2.1|P3.1"`
> （那一行的序列同时算给这几个谱表）。实测破碎音符 67.2% → **66.0%**、
> 歌词 40.1% → **26.6%**——那三个女高在合印的系统里**并不是齐唱**。
> 与上面「合流档一次都不成立」是同一个结论的两个方向。

### 版式：**从 GT 的 `<print>` 与 `<staff-details print-object>` 直接读**（`chorus-diff` 的正式尺子）

「这一段谱面印几行、哪几行」不必猜——MusicXML 自己写着：

- `<print new-system="yes">` / `new-page="yes"`：**这一小节起是新系统**；
- `<attributes><staff-details print-object="no"/>`：这个声部**从这一小节起不印**，
  遇到 `yes` 才恢复（Finale/Sibelius 隐藏空谱行就是这么写的）。

**语义照渲染那边的一份**（`src/mixed/layoutpass.ts::applyStaffVisibility`，
它移植自原 C++ 工程 `loader.cpp::processStaffDetails` + `updateSystemLayout` 的 `visPrev`）：
初值**可见**、按小节**累积**地改、`number="N"` 指**本声部的第 N 行**（钢琴可以只藏一行）、
可见性在**每个系统的首小节**取快照（系统中途的改动下一个系统才生效）。
度量与渲染共用同一套判据，别在这儿另立一份。

两处踩过的坑：

- **`<measure>` 的属性次序不固定**：首小节常写成 `<measure implicit="yes" number="1">`，
  正则要求 `number` 紧跟 `<measure ` 就会漏掉那一小节里的 `print-object`
  ——查了半天「为什么开头那个声部就印着」，就是这个。
- 一度自己拍了条「首个标志是 `yes` 就说明之前是隐藏的」的推断。**不需要**：
  上面那个正则修好之后，开头的 `no` 本来就写在第一小节里；照渲染那边的初值 + 累积改动即可。

推出来的分段与谱面**分毫不差**：

```
破碎  m1-6(2行) 只有钢琴 | m7-21(3行) +P1 | m22-45(4行) +P2 | m43-48(2行) 又只剩钢琴
      m49-82(5行) P3+P4+P5+钢琴 | m83-105(7行) 全部 | m106-109(2行)
宁静  m1-8(2行) | m9-16(3行) +Women | m17-64(4行) +Men | m65-70(2行) | m71-88(4行) | m89-(5行) +descant
```

我们的系统序列与它做**一趟一对一的 DP 对齐**（行数一样才配得上，两边都允许跳过；
一个 GT 系统只配一个我们的系统——不限的话 DP 会把所有系统塞进少数几个行数相同的段里，
实测配出来全是 0%）。配上之后第 k 行就对第 k 条**在印的**谱表，
**没印出来的小节不进分母**。

| | 音符 | 音级 | 歌词 |
|---|---|---|---|
| 按 staff·人工映射 | 83.49% | 84.02% | 85.02% |
| **按谱行·GT 推导** | **85.29%** | **85.85%** | 85.02% |

两条路互证：宁静 86.4% 对 86.1%（吻合），破碎 84.1% 对 80.9%
——差的那几点是人工映射还没修干净的版式账。**这一档已进基线**，人工映射留着当交叉验证。

> 它先查出过一处真错：**破碎五行系统的女高映射写成了 `P1.1`，真身是 `P3.1`**
> （GT 说 m49-82 在印的是 P3/P4/P5+钢琴；限定这段小节比，我们那一行对 P3 是 91.9%、对 P1 是 0%）。
> 改对之后按 staff 音符 77.98% → **83.49%**、歌词 73.19% → **85.02%**，
> 逐 staff 也各归各位：P1.1 36.4% → **75.2%**、P3.1 29.6% → **91.9%**。
> **原先那两条 30% 上下的谱表不是识别不行，是尺子指错了人。**

> **「一行罩三个谱表」为什么不成立**，这回有 GT 的账：破碎三个女高在合印的段里
> **并不是齐唱**——39 小节 P2/P3 是整小节休止、35 小节三部各不相同、35 小节两部相同。
> 既不能复制给三条，也不该把没印出来的算漏检。

### 另一半：**印谱的一行 ≠ GT 的一个声部**

破碎连成 7 条谱表（与 GT 一样多、零游离）之后仍只有 60.9%。原因在版式：
GT 五个人声是**陆续进来**的（开头连续休止 P1 有 8 个、P2 有 25 个、P3~P5 各 49 个），
而谱面上那一段只印**三行**人声（实测「2 高音 + 1 低音」），
也就是**一行谱上写着不止一个 GT 声部**。这时把跨系统的同一行正确连起来，
得到的序列必然是几个 GT 声部的混合——逐声部对拍再准也就到这儿了。
要再往前，得有一份「印谱行 ↔ GT 声部」的多对一对照，那是度量的活。

## 谱号继承（改的是 `src/staffomr/notedata.ts`）

本行没认出谱号的，**沿用上一个系统同一位置那行谱的**
（照原 C++ 工程 `Score::analyzeBarData` 的 `middleStep = prev->middleStep`）。

矢量路一直没补这一条，是因为那本书的谱号几乎都认得出；位图路认不出的有一成半。
不继承就退回 `middleStep = 41`（高音谱号的口径），低音谱行整行的音高全错。

**谱号还是 `buildScore` 连跨系统谱行的主要凭据**（`StaffToken` 的第一项就是行首谱号），
缺一行那一行会另起一个声部，一个声部因此碎成好几条——实测宁静一首
GT 5 条谱表、识别出 9 条，六成的音落在没配上的那几条里，准确率逐段漂到 0。
字典查得到 85/100 行，位置自举能到 91/100，两者并起来之后 `buildScore`
的声部数降到 5，与 GT 一致。

## 对拍：`../dev/scripts/chorus-diff.mjs`

判据一律来自 `../dev/scripts/staff-metrics.mjs`（与矢量路 `staff-diff.mjs` 共用一份）。

与赞美之泉那条的两处不同：那本是一本大 PDF 切成很多首，要先找首页、切曲目、
与 GT 配对；合唱谱是一曲一个目录，配对是现成的。那本 GT 是单声部领唱谱，
一首一条序列；合唱谱 GT 是 SATB + 钢琴的全谱，**必须逐声部比**。

### GT 与识别**都按谱表拆**（`<part>` × `<staff>`）

**不能按 `<part>` 整个拼**：钢琴那种一个声部两行谱的，MusicXML 是
「本小节第一行、`<backup>`、本小节第二行」**逐小节交替**写的，
整个拼起来是两行交织的序列，与识别侧「一行谱一条序列」根本不是一回事
（宁静的钢琴声部因此只对上 29%，按谱表拆开之后开头逐音都对得上）。

**两边都只取声部号最小的那一路**：一行谱上写两个声部时同理，
把两个声部都收进来比出来的是排列差异不是识别差异（实测 28.6% → 22.2%）。

**试过更差**：按「在系统里排第几行」分声部（想绕开 `buildScore`），
音符 25% → 13%——合唱谱的系统行数并不整齐，宁静 p1 是
「钢琴前奏 2 行、2 行，然后人声加钢琴 3 行、3 行」，
「第 k 行」在不同系统里根本不是同一个声部。

### 分**干净位图 / 真扫描件**两档

混在一个平均里，干净那一档的涨跌会被淹掉。基线只守干净档。

### `--v` 出**四等分准确率**

一眼看出「开头就低」还是「越往后越漂」——两者的病因完全不同：
前者是判据错，后者是漏音符或声部碎了。宁静一首曾经是 59%/26%/17%/0%，
那就是序列短了（422 对 GT 660），而不是读错。


## 跨系统连接：全局指派（`score.ts::assignSlots`）

`sameToken` 通配之后，剩下的串声部病根是「逐系统与前一状态做增量 LCS」，一步错步步错。
破碎逐系统剖面（谱号 + 有无词 + 音域中位数，全音阶级数）：

```
  2 行系统:                                    g— 33 | f— 25     ← 纯钢琴（前奏/间奏/尾奏）
  3 行:                              g词 31 |  g— 32 | f— 25
  4 行:                    g词 32 | g词 30 |  g— 32 | f— 21
  5 行:  g词 31 | g词 30 | f词 26            |  g— 31 | f— 20
  7 行:  g词 36 | g词 34 | g词 32 | g词 30 | f词 26 | g— 31 | f— 21
```

最后两行永远是钢琴，进出的是上面的人声；LCS 回溯天然「先配上面的」，纯钢琴系统就被配到女高女低上。

现做法：从**行数最多的那一档**定 N 个槽位（剖面取该档同位行平均），每个系统的 k 行**保序地** N 选 k，打分：

- **谱号**：两边都认得出且不同 → `CLEF_MISS -6`；一边认不出不表态（同 `sameToken`）。
- **有没有词** `LYRIC_HIT 1.5`：最硬的一条（关掉干净档 −7 点），1.0~3 之间不敏感。
- **音域中位数** `PITCH_W 0.35`、每行最多扣 4；0.2~0.55 不敏感。
- **谱面声部标签**（下节）：至少两个槽位有不同名字才表态（只有一个名字时不带信息，无条件用会扰动本来对的指派）。

共三遍：第一遍无标签；第二遍带标签，槽位标签先认「行数最满」那一档的同位行，没读出才按第一遍结果投票
（纯投票会被要挪走的行自己污染、自我强化）；第三遍拿第二遍结果重估各槽位音域基准再指派
（最满那一档往往是高潮段，音域偏高）。**同档行数之间把标签传开**（`propagateLabels`，只补空的）最值钱：
标签只在声部进入处印一次。没有剖面、或行数超过槽位数时退回增量 LCS。

### 谱面声部标签（`stafflabel.ts`）

`stafflabel.ts` 裁带 + `gen-rasterlabels.mjs` 离线 OCR + `rasterlabels.json` 缓存，架构同歌词。
运行时只按固定几何裁一条带（顶线上方、靠左），**定位交给 DBNet**（`recognizeRegion`）；带里取最靠近谱行的那一框；
拉丁名按编辑距离模糊比（容错三成，`Sopiamo` / `AItO` 都救得回）。

- 分部号 `1` 词距宽、进不了 DBNet 框，由 `digitOf` 在框右找孤立窄块单独认；候选须占框高四成以上
  （挡住 `Men,` 后的逗号读成 `1`）。
- `Sopranol` 这类形近字母按 `DIGITISH` 当分部号（名字里没有以 `l`/`i`/`z` 收尾的）。

### 试过撤掉的

| 做法 | 结果 |

| 相对纵向位置当 LCS 次级代价 | 行数一变 pos 整体伸缩；干净 82.3 → 69.8% |

（那两段音乐本来就唱得不一样高）。谱面没印标签的那一档只能另找信号。

## 读数的口径

- **headline（含游离）量的是「连接 × 识别」**，按谱行量的才是识别本身；两者之差是跨系统串声部。
  **别把 headline 换成按谱行来「达标」**，也不许靠筛难样本、缩分母、改 GT 冲数。量节选看按谱行档
  （`alignSections` 允许跳过 GT 段）。
- **按 staff** 是 `buildScore` 修到完美时的天花板；与含游离之差 = 连接的代价。连接错对歌词的惩罚远大于音符
  （一条谱表连错，整段词跟着跑到别的声部）。谱表数对上不等于每行都连对。
- **GT 范围**：`node-harness.mjs::GT_NOT_FULL_SCORE`（按曲排：主，差遣我的 GT 只有 2 个 part，PDF 是 SATB + 伴奏）、
  `GT_PARTIAL_PDF` + `gtUsable`（按文件排：`web-11-face-the-cross.pdf` 是英文试阅节选，同曲 `望十架.pdf` 照用 GT）。
  它们照旧进「无 GT」那一档的事实统计。
- **GT 开头连续的休止不算漏**（`skipLeadRests`）：合唱谱声部没进来时那一行谱不印，Sibelius GT 照写全休止。
  `errKinds` 曾没跳过，算出「漏 621 个休止」的假账。
- **小节自检不判时值**：时值一改准，原先两处错抵消凑满的小节就露馅；补回来的音记满空小节也会让它掉。
  判时值看对着 GT 逐音比的时值档。`eighth→quarter` 修了也不会让音符档动（时值只在音高对上的位置比）。
- **歌词掉一点先重跑 `gen-rasterlyrics.mjs`**：OCR 缓存按条的内容指纹寻址，判据一动缓存就落空。
- **歌词是符头查准率的探针**：`attachLyrics` 按 x 挂音节，多一个假头整行错位。凡改符头召回，别只看音符，
  「音符涨、歌词跌」几乎都是混进了假头；真净赚的形状是音符涨而歌词不动。
- 报表里「谱号 87.6%」是**逐谱表**口径，跨系统连接一错就算到谱号头上；谱号本身逐行认出 98.9%，不是瓶颈。
- **和弦档**（`--v`）把和弦当集合比：先按最低音序列对齐，再在对上的位置比成员集合。
  破碎成员命中 95.8%——和弦取舍不是病因，缺口是整音漏检。
- **读错级差**（`--v`）：整条 +2 是谱号错、±1 是线间吸错格、±7 是八度；钢琴右手读错八成偏高 2~7 级＝和弦最低音丢了。
- **错因清单别按面值读**：逐谱行「漏音数」与「读错数」r = 0.73，吸错一格 / 差一线 / 未分类多半是漏音错开对齐的下游。
- 位图路有一批判据**只拿干净位图扫过**；注里写着「扫过 x/y/z」却没提扫描件的，都该按 `--scan` 再扫一遍。
- 两档都要守：一度只守干净档，「干净涨、扫描塌」的改动一路绿灯（收竖笔画的宽度闸：扫描件 29.6% → 19.8%）。

## 排查一处错：`gen-staff-analysis.mjs`

前置：`chorus-diff.mjs --errors`（音符 + 歌词）与 `chorus-symbols.mjs --errors [--scan]`（谱号/时值/附点/临时升降/

`node ../dev/scripts/gen-staff-analysis.mjs <曲名> [--pdf=N] [--max=N]`（矢量路加 `--zmzq`）出
`staff-out/analysis-<曲名>/<底本名>/index.html`，**一份底本一个目录**、**一页一个面板**。
里面是整页底图 + 可逐层开关的叠加框、抹掉原语后的中间图、小节自检不平处、逐条错误（每条一张裁图，漏音自动带 `blameGap` 病因）。

  `chorus-diff` 与 `raster-gap` 共用）；准确率只以 `chorus-diff.mjs` / `staff-diff.mjs` 为准。

## 独唱谱测评一律按拍位规范展开（用户定）

`staff-measure-all.mjs` 原来只在 GT 多声部时过 `xmlByOnset`（和弦音拆开全数、同拍按音高排），单声部曲子的逐音序列里
和弦只数主音。可各首 GT 的主音写法不统一（有的最低音打头、有的最高音打头），而识别侧的输出顺序随「小节凑没凑满拍」变
（`toxml.ts::emitVoices` 凑满时同拍由高到低、凑不满时主音打头），于是时值一修对、小节一凑满，音符档就跟着 GT 的写法涨落
——我一生要赞美你修好四处符杠，旧口径音符 −4.4。现在所有曲子两侧都规范展开：口径与写法无关、和弦附加音也计入。
换口径那一刻合计音符 93.82 → 93.49%（多出来的分母是和弦附加音）、时值 92.31 → 92.16%，基线按新口径重写。

## 满小节的休止与全休止同一种

6/8 里一个声部整小节休止，GT 写附点二分休止、谱面印的是全休止（向主唱新歌 m14）。时值档的提取器
`node-harness.mjs::xmlStaffTypes` 按小节带上 divisions 与拍号，**时值正好一整小节的休止记 `whole`**——两侧同一个函数，口径对称；
`staff-visual.mjs` 同理（GT 满小节休止与识别的全休止不报「休止种类错」，两者都排在小节最前：全休止居中印，x 不代表起点）。
独唱谱时值 94.46 → 94.48%（只动向主唱新歌）；矢量路 `staff-diff` 各档不低于基线。

## 分系统：左侧括号优先，断开处按间距补（`page.ts::systemGroups` / `joinByGap`）

先按左端标记（系统线、方括号、花括号，罩得多的先分）分组，这一步说了算：有标记的两组之间不因间距合并，一组也不因间距拆开。
只有**左侧什么标记都没有的单行**才看间距——系统之间的空白比系统内断开处大。系统间距取本页两个相邻多行系统之间最小的空白，
单行与上一组或下一组的空白小于它的 0.8 倍就并过去；本页量不出系统间距（没有两个相邻的多行系统）就不并。
来由：望十架扫描版 p10 第二系统钢琴两行左边纸面污损，系统线与花括号都没印出来，五行被分成 3 + 1 + 1，按谱行对齐整段错配。
试过撤掉的：
- 拿本页多行系统里最大的行间空白当上限——人声行下面带歌词，系统内空白常比系统之间还大，宁静、破碎整页并乱（干净档按谱行 98.06 → 92.21）。
- 按小节线 x 对齐并（斜页上容差要放到半格）——干净档本不该并的系统也并了（按谱行 98.06 → 93.17）。
